# @venizia/vulcan-okf

Generator, conformance gate, coverage report and graph explorer for a project's knowledge bundle at
`.agents/knowledge/`, in the [Open Knowledge Format (OKF)](https://github.com/GoogleCloudPlatform/open-knowledge-format)
v0.2. Part of VULCAN; the bundle is served over MCP by `@venizia/vulcan-atlas`, not from here.

## Commands

Run through the pinned `vulcan` CLI (`bun x vulcan x okf <command>`) or the project's make targets.
The tooling reads the project it runs in (the working directory).

| Command | What it does |
|---|---|
| `check` | Gate: OKF v0.2 conformance (spec §11). Errors fail; soft-guidance warnings print and never fail |
| `check --strict` | `check` plus the house rules: every link resolves, docs style, structural coverage, freshness |
| `gen` | Regenerate all source-derived content |
| `coverage [--min <n>]` | Report the bundle against the source inventory; `--min` fails below `<n>` percent |
| `viz` | Build the offline graph explorer, `.agents/knowledge/viz.html` |

## OKF v0.2 conformance (`check`)

Exactly the spec, never stricter:

- Every non-reserved `.md` file has a parseable YAML frontmatter block with a non-empty top-level `type` (§11.1, §11.2).
- `index.md` carries no frontmatter; the bundle-root one may carry `okf_version` alone (§8, §12).
- `log.md` date headings open with a real `YYYY-MM-DD`, newest first (§9). Text after the date is tolerated - the spec is silent on it.
- Never rejected (§11): unknown types, unknown keys, missing optional fields, broken links, missing `index.md`.
- Warnings (soft guidance): `status` outside draft/stable/deprecated (§5.4), timestamps that are not ISO 8601 datetimes with an offset (§5), a `sources` entry without `resource` (§5.1), actors that are not `<producer>/<version>`, `human:<id>` or `process:<id>` (§7), an older `okf_version` (§12).

Links are bundle-absolute (`/x.md`, recommended) or relative (`./x.md`, `../x.md`, `x.md`), anchors
allowed; links inside code are examples, never edges. Files may use LF or CRLF line endings.

## What is generated vs hand-authored

Two mechanisms, both driven from source. Never hand-edit either.

1. **Whole generated files** - each renderer in `okf.renderers` writes one page - or, when its
   `render` returns an array, one page per entry - by default under
   `reference/`, with `generated.by: process:okf-gen` (§5.2). No `generated.at`: a timestamp would
   make every regeneration look like a change.
2. **Managed regions** - each `okf.regions` entry (`{ id, file, renderer }`) replaces the content
   between `<!-- okf:generated:<id> start -->` and `<!-- okf:generated:<id> end -->` inside an
   otherwise hand-authored file.

`gen` renders every page and region in memory first: a renderer that throws, a path outside the
bundle or two renderers on one path stop it before anything is written. A `gen` that changes nothing
prints `gen: up to date`.

`reference/public-surface.md` is generated by `@venizia/vulcan-atlas` (`vulcan x atlas surface gen`),
not by `gen`; its `generated:` frontmatter tells `gen` to leave it whole. Long agent-read files get a
generated contents list near the top; a file with `generated:` frontmatter and the bundle's `log.md`
get none. The id `contents` is reserved for that list: a region named `contents` stops `gen`.

A project module (`okf.renderers[]` with `module`) may take the id of a built-in renderer such as
`source-map`. The module then replaces the built-in, and `gen`, `check` and `coverage` say so once on
stderr: `okf: module 'source-map' replaces the built-in renderer`.

## Adding a renderer

A built-in renderer (`source-map`, `makefile-targets`, `packages-table`, `binding-keys`) is listed by
id, with `options`. A project's own renderer is a module:

1. Default-export `defineRenderer({ id, collect, render?, region?, coverage? })` from a file in the
   project, importing the API from `@venizia/vulcan/okf`.
2. `collect` extracts the fact from source, once. **`render`, `region` and `coverage` all read
   it** - a second heuristic for the same fact drifts, and the numbers disagree.
3. List it in the config: `okf: { renderers: [{ id, module: '.agents/okf/<file>.ts' }] }`, and in
   `okf.regions` when it renders a region.
4. Run `vulcan x okf gen`, then `vulcan x okf check --strict`: it passes, and a second `gen` prints
   `gen: up to date`.

The [renderers reference](../../docs/wiki/content/references/okf/renderers.md) shows a complete module.

## Layout

| Path | Role |
|---|---|
| `src/cli.ts` | `vulcan-okf` entry; spawns `src/run.ts`, the command runner |
| `src/index.ts` | the public API: the OKF v0.2 conformance layer |
| `src/source/` | source scanning and the shared fact collectors (one per fact, used by gen and coverage) |
| `src/generate/` | `gen`: the built-in renderers, project modules (`defineRenderer`), regions and contents lists |
| `src/check/` | `check`: OKF conformance, plus the house rules under `--strict` |
| `src/coverage-report/` | `coverage`: the bundle against the source inventory |
| `src/lib.ts` | bundle loader: frontmatter, links, concept model |
| `src/spec/` | OKF v0.2 conformance - pure, never throws |
| `src/viz/` | explorer: builder (Bun), typed browser client, template |
| `src/project/` | reads the project config `vulcan x` hands okf - everything project-specific |
| `src/config.ts` | constants that hold for every project: pruned directories, reserved files |
