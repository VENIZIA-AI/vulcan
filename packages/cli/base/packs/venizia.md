# Rules - the Venizia pack

<!-- Shipped by @venizia/vulcan, never edited in a project. These rules bind the Venizia stack (Bun, devz, the vite
     builders, the house lint rules), so they are not in the base rules: a project turns the pack on with
     `packs: ['venizia']` in `.configs/vulcan.config.*`, and `vulcan sync` names it in the rules block of AGENTS.md.
     The IDs are the ones they had in the base rules and keep their `V-` namespace. -->

Cite by ID. Every rule has "Enforced by".

| ID | Rule | Enforced by |
|----|------|-------------|
| V-B-05 | **One script set for every app**, backend and frontend: `server:dev` (`NODE_ENV=development bun run src/index.ts` for a backend, `vite --config .configs/builders/vite.config.mts` for a frontend), `compile` (`bun .configs/builders/compile.ts` for a backend, `vite build --config .configs/builders/vite.config.mts` for a frontend), `typecheck` (`bun check`), `lint` (`devz lint`), `lint:fix` (`devz lint --fix`), `test` (`bun test`), `clean` (`devz clean`). The logic lives in `.configs/builders/` or in `devz`, never in the `package.json` string. No `dev`, `start`, `build`, `rebuild`, `preview` or `server:prod`; a domain extra such as `migrate:dev` is fine. **An app root holds only `.configs/`, `src/`, `package.json`, `tsconfig.json` and `.env.example`**; every other config lives in `.configs/{lints,formatters,builders}/`. A library package keeps Makefile targets: `build`, `typecheck`, `lint`, `lint-fix`, `test`, `clean`. | SOFT |
| V-B-09 | **Agent scripting uses bun by default.** A script you write to do a task is `bun -e '…'` or `bun file.ts`, with `Bun.file()` for files. Python or another language is allowed when the task needs it - an existing project script, a tool only that language has - and you say so in one line. | SOFT |
| V-C-07 | **A function name opens with its verb** - `generate` `build` `to` `is` `has` `assert` `extract` `enrich` `get` `resolve`. `is*` returns a boolean and leaves the branch to the caller; `assert*` throws and returns `void`; `has*` is the ownership question (`hasBucket`, never `isBucketExists`). That list is for UTILITY functions; service methods lean on a wider set. **Arrow functions, not `function` declarations** (do not churn existing ones). State plus the operations on it live in a class with static members - the `LoggerFactory` shape - never module-level `let` plus exported arrows. | SOFT |
| V-C-08 | **Enumerable strings are a const class plus `TConstValue`,** never a raw string-literal union. When something validates against such a class, it carries `static readonly SCHEME_SET = new Set([...])` over its values and `static isValid(value: string): boolean` reading it, so a runtime check exists wherever a value crosses a boundary (a subclass redeclares `SCHEME_SET` with `...Parent.SCHEME_SET` first); a class nothing validates against needs neither. The `T`/`I` prefix follows the declaration keyword: `type` gets `T`, `interface` gets `I`; an interface turned into a type alias is renamed. | SOFT - lint (`const-class-values`) in a project that enables `houseConfigs` of `@venizia/dev-configs` |
| V-C-20 | **Declare the instance, then await on its own line.** Never `await new X({...}).method({...})`: write `const runner = new X({...});` and then `await runner.run({...});`. A constructor inside an awaited call chain hides the object that does the work - a reader cannot name it, a second call cannot reuse it, and a failure in the constructor reads like a failure in the method. A longer chain (`await new X().a().b()`) is the same defect. It covers tests and scripts. `await new Promise(...)` is not this form: the constructor call is the awaited value itself and the promise needs no name. | SOFT |
