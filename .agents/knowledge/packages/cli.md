# cli - `@venizia/vulcan`

| Command | What it does |
|---|---|
| `init` | Scaffold the project layer; never overwrites. Writes `.configs/vulcan.config.mts`, appends the agent entries to `.gitignore`, installs the lint tools it configures, ends with a numbered list of what is left |
| `init --preset` | Create a new monorepo with its first app from a framework preset (`packages/cli/src/create/`); refuses a folder that is not empty |
| `add --preset` | Add an app (`--app`), a library other apps import (`--lib`) or a side-neutral shared package (`--shared`) from a preset to a monorepo `init --preset` created |
| `sync` | Write the gitignored agent adapters; takes back what the config no longer asks for; prints the base rules added, changed or removed since the manifest last recorded them |
| `doctor` | Check the project contract; exit 1 on any violation |
| `commit-check` | Check a commit message (`<file>`, `--text`, `--range`) against `commit.message` in the manifest: an agent signature (`AgentSignature.find`; the products, mentions, address names and domains, noreply domains and generated phrases are data in `base/commit-agents.json`; `commands/index.ts` loads each command when it runs, so this one never loads atlas and a test walks the static imports to keep it so) and the project's optional subject pattern; exit 1 on a problem, 2 on bad input, 0 with a note when no check is configured |
| `ci` | `ci affected --base <ref> [--head <ref>] [--check c] [--json \| --names]` lists the workspace packages a change touches with their checks; `ci template github\|gitlab` prints a CI template. Exit 2 on bad input, 0 otherwise (an empty list too). Loaded lazily, never loads atlas, zod or the config |
| `board` | `board [--out f] [--open] [--since d] [--dir d] [--repo owner/name]... [--no-github]` folds the event log (and `gh pr list` of each repo) into flows and writes one read-only HTML page (default `.agents/local/reports/board.html`). Exit 2 on bad input, 1 when the file cannot be written. Loaded lazily; it never loads atlas or the config |
| `event` | `event add --kind <k> --summary <text> [--flow F-n] [--ref r] [--actor a] [--dir d]` appends one line to the agent event log and prints its id; `event tail [--since t] [--json] [--dir d]` reads it (default: the last 24 hours, oldest first); exit 2 on bad input, 1 when the folder cannot be written. Loaded lazily like `commit-check` (never loads atlas) |
| `upgrade` | Install the target (`--stable`: `latest`, the default; `--nightly`: the higher of `latest` and `next`; a named version wins), then sync with the newly installed CLI |
| `x <okf\|atlas>` | Run a shipped tool at the pinned version, on the inherited stdio |

`@venizia/vulcan` depends on okf and atlas at the exact same version.

## Presets, `init --preset` and `add`

A preset is a framework's app template: `preset.json` plus a `files/` folder, found through `vulcan.presets.app` (and `vulcan.presets.lib` for a library kind, `vulcan.presets.shared` for a side-neutral shared kind with the lib file's keys and the tokens `{{project}}`, `{{shared}}`, `{{package}}`; `app` stays required) in the framework's `package.json`; a shared package records `presetKind: 'shared'` on its config entry (`vulcan sync` copies it into the manifest, and atlas reads it) and a `shared` summary on the preset record, and a VULCAN that predates both cannot read that config. It is data only; VULCAN never runs code from it, and `presetVersion` is `1`.

- A name asked in a terminal or taken from a flag; none has a default (`--project`, `--backend-dir` or `--frontend-dir`, `--app`, `--shared-dir`). A bare `--preset <name>` means `@venizia/<name>`; `file:<path>` is for tests.
- `files/` is copied with `{{project}}`, `{{app}}`, `{{devPort}}` and `{{apiUrl}}` replaced; only `_gitignore`, `_npmrc`, `_env` and `_env.example` are written as dotfiles (npm drops dotfiles); binary files are copied byte for byte, symlinks are skipped, and `vulcan.presets.app`, `files` and every `checks` entry are validated (inside the package, a key of `scripts`).
- The config keeps `layout`, `packages` and the preset's `atlas` sources between the `vulcan:apps:start` and `vulcan:apps:end` comments. `add` rewrites only that block, and refuses with the lines to paste when the markers are gone.
- `add` keeps the catalog's versions over the preset's, refuses a preset whose `peers` the catalog does not satisfy, and picks the next free port from the apps' `.env.example`.
- `urls` (optional, paths starting with `/`) is what the closing `Next:` block opens, one `open http://localhost:<port><path>` per path; absent means the root. `init` records it in the app's `package.json` as `vulcan.urls`, so `add` prints every app's urls, and an app made before keeps the root. The block is `create/next.ts`. `add` without a terminal checks `--app`, the side folder and `--api`/`--no-api` before it downloads, as far as the flags name the side. The root `.gitignore` `init` writes ignores `*.tsbuildinfo`.
- `vulcan preset diff <package>` (an app, a library or a shared package; a library or shared package takes the one recorded preset that ships its kind, else `--preset`) (`create/preset-diff.ts`, `create/diff.ts`; read-only): renders the preset's files with the app's own tokens through `Preset.renderFiles` (the render `Preset.copyFiles` writes) and sets each against the app's file: `same`, `differs` (`+N -M`, `--full` the unified diff), `missing`. The preset is found from the app's `package.json` dependency and the config's recorded `presets` (`--preset` overrides); the version is the installed one in the app's `node_modules` (bun's isolated linker) or the root's, a `file:` folder, or a scratch fetch for `--preset name@range`. `--check` exits 1 on drift; a library or shared package is reported as "the package" where an app is "the app". No apply, no merge, no per-app record.
- `VULCAN_NO_INSTALL=1` (tests only) prints the install, `git init`, `sync` and the checks as `skipped` lines. An npm preset needs the install, so the tests use `file:` presets (`src/__tests__/fixtures/preset-*`). `VULCAN_BUN` and `VULCAN_GIT` (tests only) replace the `bun` and `git` executables, so a test can make an install or `git init` fail without the network.
- `doctor` has an `apps` check: every `backend`, `frontend` and `shared` folder of `layout` is a workspace (`ProjectScaffold.coversFolder` also accepts a glob that matches a package there, such as `auroras/*/*`), and every package lives in a listed folder, `layout.other` included. `layout` folders are paths (`common/layout-folder.ts`: 1 to 4 segments, no `..`, no leading or trailing slash, no backslash, no `node_modules`, unique across keys and never nested), a side may list several, and `other` lists folders the layout leaves alone; the schema, `add`, `doctor` and `guard-package` share that one validator.

Wiki pages: `references/commands/init.md`, `references/commands/add.md` and `references/presets.md` under `docs/wiki/content/`.

## Prompts

Questions go through `packages/cli/src/ui` (wrappers over the pinned `@clack/prompts`), never clack directly. `TerminalCapability.menusAvailable()` (stdin and stdout TTY, `TERM` not `dumb`) picks menus; every other case keeps the plain line questions (`askWithPrompt`) so pipes and logs are unchanged. A pty test drives a menu with `driveTerminal` (`__tests__/terminal.helper.ts`); the older pty tests set `TERM=dumb` to keep covering the plain questions. Every prompt runs inside `MenuInput.guardAgainstPipedLines` (`ui/keyboard.ts`): a raw-mode keyboard sends CR for Enter, so the first LF while a menu is open means piped lines, and the command restores the terminal and exits 1 naming the flags and `TERM=dumb`.
