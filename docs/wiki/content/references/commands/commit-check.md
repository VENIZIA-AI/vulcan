# vulcan commit-check

`vulcan commit-check` rejects a commit message that signs the commit as an agent, and checks the one-line subject shape when your project gives one. Nothing is checked until the project turns a check on.

```text
$ bun x --no-install vulcan commit-check .git/COMMIT_EDITMSG
commit-check: 1 problem(s) in the commit message:
  commit message, line 3: "Co-Authored-By: Claude <noreply@anthropic.com>" signs the commit as an agent; remove the line
```

## Turn it on

Add the key to `.configs/vulcan.config.mts`, then run `vulcan sync`:

```ts
export default {
  commit: { message: { agent: { signature: 'deny' } } },
};
```

`sync` writes the key to the manifest, which the command reads, and installs the [`commit-msg` hook](#the-hook) in your clone. Every developer gets it on their next `sync`. The [config reference](/references/configuration/#commit) lists every key.

## Claude Code's own attribution

With `agent.signature: 'deny'`, `vulcan sync` also turns off the attribution that Claude Code adds itself, so the signature is not written in the first place. It adds this to the managed `.claude/settings.json`:

```json
{ "attribution": { "commit": "", "pr": "", "sessionUrl": false } }
```

An empty `commit` or `pr` hides the attribution text of commits and pull request descriptions, and `sessionUrl: false` leaves out the `Claude-Session` trailer and the session link that web and Remote Control sessions add. The names come from the settings schema of Claude Code 2.1.317. Switching back to `'allow'` and running `sync` removes exactly that key, and only while it still holds what `sync` wrote: a value you changed by hand stays. This applies only when Claude Code is one of the agents you chose on that machine.

| Agent | Setting | VULCAN |
|---|---|---|
| Claude Code | `attribution` in `.claude/settings.json` | Written by `sync` |
| Copilot in VS Code | `git.addAICoAuthor` in VS Code settings, default `off` | Not written: it is a VS Code setting, in a file that allows comments, and it is already off by default |
| Cursor | `attribution.attributeCommitsToAgent` in `~/.cursor/cli-config.json`, a per-user file | Not written: nothing outside the project is changed, and Cursor's staff report that the local executor ignores it |
| Copilot CLI | no setting found; a feature request for one (github.com/orgs/community/discussions/203517) says there is none | Not supported |
| Codex | no setting found in its configuration docs | Not supported |
| omp, Antigravity | no co-author trailer found in the installed omp 18.13.2 and agy 1.4.7 | Nothing to turn off |
| Pi | not checked | Not supported |

For every agent the `commit-msg` hook is the check that catches a signature the settings did not prevent.

## Usage

Give it one message:

| Input | Checks |
|---|---|
| `<message-file>` | The message in that file. This is what the `commit-msg` hook passes |
| `--text <message>` | The text you give |
| `--range <revs>` | Every commit of a git range, such as `origin/develop..HEAD`. Use it in CI |

Exit codes: `0` when nothing is wrong, or when no check is configured (it says so on stderr); `1` when a message has a problem; `2` for bad input, checked before it looks at the configuration: no input or more than one, an unknown flag, a file it cannot read, a range git rejects. `--range` takes a revision only; a value that looks like an option is refused.

Run it at the project root. It reads `.agents/vulcan.manifest.json` from the current folder and does not search upward, so from a subfolder it finds no manifest, says that no commit check is configured, and exits `0`. The generated `commit-msg` hook changes to the top of the repository first; a hand run, and `--range` in CI, need the root.

## What it checks

**An agent signature** (`commit.message.agent.signature: 'deny'`). A line is a signature when it is:

- a `*-by:` trailer (`Co-Authored-By`, `Co-developed-by`, `Assisted-by`, `Signed-off-by`, and so on) whose name begins with an agent product as whole words (`Claude Code`, `Claude Opus 4.5`, `GitHub Copilot`, `Cursor Agent`, `Codex`, `ChatGPT`, `GPT-5`, ...), or whose address is an agent's: a `noreply`, `no-reply` or `no_reply` address at an agent vendor's domain, or an address whose local part is an agent's name at a domain an agent uses (`cursoragent@cursor.com`, `codex@users.noreply.github.com`);
- a `Generated with` or `Generated by` line, at the start of the line, with an agent's name right after it (`Generated with Claude Code`, `Generated by [Claude Code](...)`). A link alone does not count, and neither does a name later in the line: `Generated by scripts/gen.ts from CLAUDE.md` is a note about a file.

Spaces, case, hyphens and invisible characters do not matter: `ClaudeCode`, `Claude-Code` and `Claude Code` read alike, and so do a non-breaking hyphen in `Co-Authored-By` and a zero-width character inside a name. But words are whole: `Claude Coderre`, `Gpta Rao` and `Anthropic-fan Bob` are not products.

Git's comment lines and the scissors line follow the repository: `#` by default, `core.commentChar` or `core.commentString` when set, and any character git may pick when it is `auto`. A comment line is not read, and nothing below the scissors line that `git commit -v` writes is read. A CRLF, and a lone carriage return, is a line break, and line numbers count each one.

A human co-author passes: `Claude Dupont <claude.dupont@example.fr>`, `claude@martin.fr`, `Jane (Cursor team) <jane@cursor.sh>`, a person at a vendor's domain with a normal address, a note such as `Generated with protoc`, and a tool named in the subject. A name alone, such as `Claude`, with an address that is not an agent's, is not flagged.

The products, vendor domains, address names and phrases are data, in `base/commit-agents.json` of the package. Add your own products with `commit.message.agent.names`; a project cannot remove a shipped one. List a person who shares a name with an agent in `commit.message.agent.allow`: a co-author whose whole name is that entry, with an address that is not an agent's, is not flagged. `allow: ['Claude']` clears a person called Claude, never `Claude Code`. Every entry of `names` and `allow` needs a letter or a digit; the config refuses `-` or a blank.

**A subject shape** (`commit.message.subject`). The first line that is not a git comment must match the regular expression you give. VULCAN ships no pattern, because the shape belongs to each project. Merge, `Revert`, `fixup!`, `squash!` and `amend!` subjects are not checked.

```ts
commit: {
  message: {
    agent: { signature: 'deny' },
    subject: {
      pattern: '^(\\[#\\d+\\])+ (feat|fix|docs|refactor|test|chore)(\\([^)]+\\))?: .+$',
      hint: '[#N] type(scope): subject',
    },
  },
},
```

## The hook

`vulcan sync` installs `commit-msg` in your clone when a check is on. Git runs it for every commit, so it covers each coding agent and a person committing by hand.

| Your clone | What sync does |
|---|---|
| No `commit-msg` hook | Writes `.git/hooks/commit-msg` (a linked worktree shares the hooks of its repository) |
| A hook written by sync | Updates it when the template changed; removes it when you turn every check off |
| A hook written by sync for another project of the same repository | Leaves it. A repository has one `commit-msg` hook and it belongs to the project that wrote it: `sync` prints `skipped` and whose it is |
| A hook of yours | Leaves it. `sync` prints `skipped` and the line to add: `bun x --no-install vulcan commit-check "$1"` |
| `core.hooksPath` set (for example `.githooks`) | Writes nothing there. `sync` prints the same line for that folder's `commit-msg` hook |
| A symbolic link in the hook's place | Leaves it and says so |
| A project folder whose name holds a line break or another control character | Writes nothing. `sync` prints `skipped` with the reason, and `vulcan doctor` reports the hook as not running the check |

sync never overwrites a hook it did not write; it knows its own by the marker on the second line, which also names the project folder it was written for (`[]` for the top of the repository, `[apps/web]` for a project below it); a hook with a marker for another folder is another project's and is never rewritten or removed. A hook from an earlier release has no folder and counts as the top level's. The hook that sync writes lets the commit through, with a note on stderr, when bun is not installed, `node_modules/@venizia/vulcan` is found neither in the project folder nor above it up to the git top level, or the installed vulcan has no `commit-check` command (an older branch). A hook that blocks every commit of a fresh clone does more harm than the gap. That promise covers the hook sync writes: a hook of your own that calls the command, such as VULCAN's own `.githooks/commit-msg`, blocks on any failure unless you write it to pass. `git commit --no-verify` skips it, as it skips any hook, so this is a check against drift, not a sandbox. Run the check in CI with `--range` to catch what a skipped hook let through.

`vulcan doctor` warns when a check is on and the hook is missing, out of date, or not calling the command ([commit-hook](/references/commands/doctor#commit-hook)).
