This release adds `vulcan migrate` and a changelog folder per version, a board that updates by itself, GitLab support and a lighter set of shipped hooks. It trims the base rules and removes several hooks and config keys, so a project must run `vulcan sync` after it updates and may have a key to delete.

## Breaking
- **Seven shipped hooks are removed** `shipped-hooks-removed` (`@venizia/vulcan`): `guard-manifest`, `guard-package`, `guard-remote-hosts`, `guard-scripting`, `stop`, `prompt-submit` and `post-tool` no longer exist. Nothing refuses a write to the generated manifest or a hand-written `package.json` at the call (`vulcan doctor` still fails a stale or hand-edited manifest), no host is asked about, no reminder follows a python command, a reply is not checked against the report shape, and no line or note is written for each prompt or tool call. Every project that ran `vulcan sync` with an earlier release is affected: the `.claude/settings.json` entries of the three guard hooks block every Bash and write call once their files are gone (only a bare `bun install` passes). After updating, run `bun install`, then `bun node_modules/.bin/vulcan sync` in a terminal, not through the agent. Sync drops the old entries and keeps a hook of your own on the same event. The files `.agents/local/violations.jsonl`, `.agents/local/cache/signals.jsonl` and the folder `.agents/local/cache/replies/` are left behind and can be deleted.
- **The `remoteHosts` config key is removed** `remote-hosts-key-removed` (`@venizia/vulcan`): a config that still sets `remoteHosts` is refused and the error names the key. The personal file `.agents/hooks/trusted-hosts.local` is no longer read. A project that wants a question before a command reaches a host puts the rule in the host's own permissions, for example `permissions.ask` under `claude.settings`.
- **The `claimWords` and `shortReplyWords` owner keys are removed** `owner-report-keys-removed` (`@venizia/vulcan`): `owner.report.claimWords`, `owner.report.shortReplyWords` and `shortReplyWords` in `.agents/local/profile.json` were read only by the removed reply check; they are refused with a pointer. `owner.report.enforce: 'block'` still loads and blocks nothing: `off` leaves the report-shape card out of the session digest, `advise` and `block` print it.
- **The `guard.writes.trustedScripts` key is removed** `guard-writes-trusted-scripts-removed` (`@venizia/vulcan`): `guard-writes` no longer opens scripts, so a config that lists `trustedScripts` is refused until the key is deleted. A deploy or migration hidden inside a script is no longer asked about: put the command that starts it in `guard.writes.commands`, or in Claude Code's `permissions.ask`.
- **The `hooks` config key is removed** `hooks-config-key-removed` (`@venizia/vulcan`): a project hook now goes under `claude.settings.hooks`, in Claude Code's own settings shape. A config that still has a `hooks` array is refused, and `vulcan doctor` no longer has the `hooks` check.
- **The `knowledge.syncAreas` key and the knowledge-sync skill are removed** `knowledge-sync-areas-removed` (`@venizia/vulcan`): the audit of the knowledge bundle is now a section of the `docs-update` skill. A config that sets `knowledge.syncAreas` is refused; delete the key and the map file it pointed to. `vulcan sync` takes back the `knowledge-sync` skill link.
- **`vulcan ci` and the `ci` config key are removed** `ci-command-removed` (`@venizia/vulcan`): `vulcan ci affected`, `vulcan ci template` and the `ci` key are gone, and a config that sets `ci` is refused. A pipeline that called `vulcan ci affected` needs its own change detection.
- **`vulcan x okf viz`, `make okf-viz` and the `okf.viz` and `okf.sections` keys are removed** `okf-viz-removed` (`@venizia/vulcan-okf`, `@venizia/vulcan`): the offline knowledge graph explorer has no replacement. A config that sets `okf.viz` or `okf.sections` is refused. The brand it carried is now `okf.brand`, and `cytoscape` and its layout packages are no longer dependencies of `@venizia/vulcan-okf`.
- **`okf check --strict` reads the code the wiki shows** `okf-docs-code-rules` (`@venizia/vulcan-okf`): a fenced `ts`, `tsx`, `js`, `jsx`, `mts` or `mjs` block in `knowledge.wiki` now fails the check on an explicit cast, `any` as a type (also as a generic default or bound, in an import or export list, and after `satisfies`), a conditional spread or a string-literal union. `as const` and the renames of `import { A as B }` are not casts. A generated page, strings, template literals and comments are not read, `<!-- docs-code: off -->` and `on` leave out a quoted signature, and each page that uses an off region is listed with a count. A table cell over 120 characters is a warning only. Changelogs are not read.
- **The base rules go from 50 to 36, and twelve rule ids are gone** `base-rules-trimmed` (`@venizia/vulcan`): `V-W-04`, `V-S-07`, `V-P-01`, `V-P-03`, `V-P-09`, `V-B-01`, `V-B-06`, `V-C-12`, `V-C-15`, `V-C-16`, `V-C-17` and `V-C-19` were merged into a surviving rule or deleted, and a removed id is never reused. A project whose `.agents/rules.md` says `Extends` one of them fails the `rule-ids` check of `vulcan doctor` until it names the rule that took its place; `V-W-04` became `V-W-06`, `V-S-07` became `V-S-01`, `V-P-03` became `V-P-02`, `V-P-09` became `V-P-11`, `V-B-01` became `V-B-04`, `V-B-06` became `V-C-11`, `V-C-12` and `V-C-16` became `V-P-08` and `V-C-19` became `V-C-02`; `V-P-01`, `V-C-15` and `V-C-17` have no successor. One rule is new: `V-S-08`, no package run by name (see the Security item on runners).
- **The Venizia-stack rules move to a rule pack** `venizia-rules-in-a-pack` (`@venizia/vulcan`): `V-B-05`, `V-B-09`, `V-C-07` and `V-C-08` leave the base rules with their ids and live in `base/packs/venizia.md`, together with the new `V-C-20` (declare the instance, then await it on its own line). A project follows the pack with `packs: ['venizia']` in its config; without it the project is no longer held to those rules, and a project rule that cites one of them is told which pack holds it.
- **A theme whose colours fail the contrast check no longer loads** `theme-contrast-check` (`@venizia/vulcan`): every explicit colour pair of `theme` is checked against WCAG AA (4.5:1 for text, 3:1 for a mark). A config that loaded before, an `accent` alone included, can stop loading; the error names the pair, the colours and the ratio.
- **`vulcan event add --flow` refuses an id no line of the log carries** `event-add-flow-must-exist` (`@venizia/vulcan`): `--flow` used to accept any `F-<n>` and wrote it; it now exits 2 with `no flow X in the log` when no line carries that id, so a script, hook or agent that passes a typed or stale id fails. Start a flow with `vulcan event add --kind flow --title ...` and pass the id it prints; a flow id is `VULZ-<project.key>-<number>`, which needs `project: { key }` in the config.
- **Config values atlas hands to git or reads from a tag template are refused when the config loads** `atlas-config-values-refused` (`@venizia/vulcan`, `@venizia/vulcan-atlas`): an `atlas.sources` entry over `http://`, `git://` or `ext::`, a `repo` or `ref` that starts with `-`, and a `name` that is not letters, digits, `.`, `_` or `-` (starting with a letter or digit) are refused, and so is a `<package>` or any placeholder other than `<dir>`, `<version>`, `<issue>` and `<date>` in `atlas.tagPattern` and `atlas.legacyTagPatterns`. The error names the value, and `vulcan sync` and `vulcan doctor` stop until it is fixed. A source whose tarball is over the new default of 128 MiB also needs a higher `atlas.limits.download`.
- **`guard-writes` no longer opens scripts** `guard-writes-reads-no-scripts` (`@venizia/vulcan`): `bun x.ts`, `node x.js`, `bash deploy.sh` and a package script were read for a deploy, a migration or an HTTP write and asked about; they are not read now. A project that relied on that for its own deploy or migrate script lists the command in `guard.writes.commands` or in Claude Code's `permissions.ask`.
- **`make wiki-links-check` checks the folders of your layout** `wiki-links-check-reads-the-layout` (`@venizia/vulcan`): with a `layout`, `make wiki-links-check` can now fail where it passed: the checked folders are the ones it names plus `docs/`, `scripts/` and `.agents/`, so `packages/` and `examples/` are no longer checked unless they are in `layout.other`, and a layout folder that was not checked before can now fail the check. With no layout the list is unchanged.
- **`vulcan clean` removes only stale items by default** `clean-keeps-items-in-use` (`@venizia/vulcan`): in `tmp/` that is older than a day and in `clones/` older than two weeks; fresh items are listed as kept, so a script that emptied the folder now leaves them. `--include-fresh` takes them too, and `tmp/claude-<uid>` is never removed. A script that emptied `tmp/` with `vulcan clean --yes` adds `--include-fresh`.
- **A remote atlas source keeps the commits of five refs** `atlas-source-cache-keeps-five-refs` (`@venizia/vulcan-atlas`): each remote source keeps the commits of the five refs it served last, so the cache stops growing with every pinned release; an offline start for a ref that is not among those five needs the remote.
- **A version folder in progress must carry a summary, highlights and upgrade steps** `changelog-reading-keys-required` (`@venizia/vulcan`, `@venizia/vulcan-atlas`): `vulcan changelog check` fails a version folder without `released:` when its `log.md` has no `summary` (one sentence of at most 200 characters) or no `highlights` (one to five lines of at most 110 characters, at least three when the folder holds three or more items), when a block of its `migration.yaml` has no `upgrade.steps`, or when its opening paragraph names `migration.yaml`. A released folder is checked for none of it, and may gain a `summary` and `highlights` later without breaking its freeze.

## Added
- **Move a package between two releases with `vulcan migrate`** `migrate-plan-and-apply` (`@venizia/vulcan`, `@venizia/vulcan-atlas`): `vulcan migrate plan --to <version|latest|next>` lists what your code must change to move a `@venizia/*` package to another version, newer or older, with the file and line of each place it touches. `vulcan migrate apply` runs the codemods of the plan in order, once each and prints the manual steps; it refuses an app with uncommitted changes or outside a git work tree, a plan that is degraded or behind npm, and a plan made while a source was not served, unless you pass `--force`. The atlas tool `migrate` gives an agent the same plan as JSON and edits nothing. The plan says what it could not check: how many changelog entries the window holds and how many have structured steps, breaking entries with none, a source atlas could not serve (a warning), an atlas ref behind the version npm calls `next` or `latest`, and a re-export or a whole-module import (counted, not listed; `--verbose` lists them). Installed packages no source serves are one line. It runs from any folder of a project. It compares the changelog state at the two versions, so an item added and taken out between two prereleases shows nothing, one taken out is undone and one that changed is undone and applied again. Each step names its direction and `apply` runs `--reverse` on the downgrade steps only. Each codemod runs with the runner of the project that serves the package (`knowledge.codemodCommand`, default `devz codemod`), and only when its binary is installed inside a package of that project.
- **A changelog can be a folder per version** `changelog-version-folders` (`@venizia/vulcan`, `@venizia/vulcan-atlas`, `@venizia/vulcan-okf`): `changelogs/<version>/log.md` (Keep a Changelog sections in the order Breaking, Deprecated, Added, Changed, Fixed, Security; each item is a line of a bold title, the item id in a code span, an optional package list and prose) with a `migration.yaml` beside it, keyed by item id, states the net change from the previous stable. `vulcan changelog check` fails a Breaking or Deprecated item with no block, a block with no item, a repeated id, sections out of order and more than one line in progress; `--history --base <ref>` also fails a released folder that changed, a stable with no folder and a dated file, dated after `knowledge.datedUntil`, added or edited. `vulcan changelog notes --version <version>` prints the body of `log.md` and the packages, and with `--migration` the path of `migration.yaml` when it holds a block. A dated entry keeps working: a Breaking Change entry on or after the date in `knowledge.migrationFrom` carries a `migration:` block. `knowledge.migrationFrom` also takes a version, `knowledge.datedUntil` is the last date a dated file may carry, and `knowledge.codemodCommand` sets the codemod runner; `@venizia/vulcan-atlas` exports `VersionFolders`. `okf check --strict` checks the `packages:` of a `log.md`, and `vulcan doctor` fails a project that holds version folders while its installed `@venizia/vulcan` is older than the atlas that reads them.
- **`vulcan runners check` finds every package a project runs by name** `runners-check` (`@venizia/vulcan`): it lists each tracked file that runs an unscoped package through `bunx`, `pnpx`, `bun x`, `npx`, `npm exec`, `pnpm dlx` or `yarn dlx` (also behind `corepack`), with or without `--no-install`, as `file:line` (exit 1). A scoped package (`@scope/name`) passes, and so do the names in the new `guard.runners.allow`; tests, lockfiles, build output and frozen history are not read. A flag the check does not know takes the next word, so it cannot hide the name. In a Markdown file, a line or a fenced block after the comment `<!-- runners: example -->` is an example of a refused command: it is not a finding, and the check prints how many it set apart (a script, a workflow or a Makefile has no such comment). Run it in CI.
- **`symbol` names where a declaration came from, and `vulcan x atlas status` shows what atlas reads** `atlas-symbol-origin-and-status` (`@venizia/vulcan-atlas`): a remote source's `symbol` answer carries `origin` with the version and the installed folder it read (no folder means the newest published release answered because none is installed), and `vulcan x atlas status` lists the sources, the copy of each `@venizia/*` package atlas reads and every other copy, with a note when their versions differ.
- **The atlas reads the version folders** `atlas-reads-changelog-folders` (`@venizia/vulcan-atlas`): `search` and `get` cite an item as `changelog:<version>#<item-id>` with its migration block under it, and `changes` lists the items of a version window with their block and reports the short `Breaking` badge as `Breaking Change`. A dated file that a folder covers is left out of a window that holds the folder's items and kept in one that does not, so no change is listed twice or lost. A cached source whose release table holds no changelog entry although its commit has some is pulled again instead of being served as empty, and an index built before this release is rebuilt locally once.
- **The symbol tool serves a declaration, and atlas writes an API page per package entry** `atlas-declarations-and-api-pages` (`@venizia/vulcan-atlas`, `@venizia/vulcan`): `symbol` answers with the exported declaration, its TSDoc and members, the internal types it uses and the declarations of the exported types it refers to, with `truncated: true` when something was left out. `vulcan x atlas api gen` and `check` write and verify `references/api/<entry>.md` under `knowledge.wiki`, one page per package entry, and `api undocumented` lists exports with no TSDoc, reading `.ts` source for a package that publishes it. `--package` takes the dir id, the npm name or the path from the project root, and a value that matches no package stops the command with exit 2.
- **The board updates by itself with `vulcan board serve`** `board-serve` (`@venizia/vulcan`): `vulcan board serve [--port <n>] [--open] [--since <date>] [--dir <folder>] [--repo owner/name] [--no-github]` serves the board on `127.0.0.1` and sends the open page a new snapshot when the event log changes. The address carries a token, defaults to `http://vulz-board.venizia.ai.localhost:<port>/` (or the name in `board.hostname`, lower case and ending in `.localhost`), and the port defaults to 4317. Every request needs the run's token and a local host and origin. The command `vulcan board` and its flags are unchanged.
- **The board reads GitLab** `board-reads-gitlab` (`@venizia/vulcan`): set `provider: { type: 'gitlab', host? }` and `vulcan board` adds merge requests, approvals, finished jobs and commits through `glab`, joined to flows by `Flow: <id>` in a description, branch or commit message. Without `provider` the board reads GitHub as before. Run `vulcan sync` and `glab auth login` once.
- **A flow has a title, lists and a project-made id** `event-flows` (`@venizia/vulcan`): `vulcan event add --kind flow --title ... --why ... --context ... --next ...` names a flow, and `--step`, `--step-done`, `--check`, `--check-done`, `--app`, `--due` and `--ref` carry its checklists, apps, due day and tracker id; the newest `flow` line of a flow wins as a whole. `--kind deploy` says something went live, and a session start records its model. A flow id is `VULZ-<project.key>-<number>`: set `project: { key: 'KEY' }` (2 to 8 upper-case letters or digits, written by `vulcan init`, which takes `--key <KEY>`; `vulcan doctor` warns when the event log is on and `project.key` is not set), and the command assigns the number, so ids never collide. `--flow` is checked against the log (see the Breaking item `event-add-flow-must-exist`); an old `F-n` id that a line of the log carries keeps working. The rule `V-P-13` asks an agent to name its flow this way in a project with `events.log` on, and `board.agents` values may be `{ shape?, lane?, role? }`. An older vulcan reading the log skips the new kinds.
- **A project can make the outside-the-project guard refuse** `guard-outside-deny` (`@venizia/vulcan`): `guard.outside: 'deny'` makes `guard-outside` refuse a write outside the project where it asks by default, for agents that run in an auto mode where an ask can be approved unseen. A line the guard cannot read (a program named by a variable, a quote that never closes, a target it cannot work out) is asked about in both modes; a path it read outside the project is denied. `guard.toolOwnedPaths` still passes. The settings are written to the manifest by `vulcan sync`.
- **A project can name a short temporary folder** `local-tmp-folder` (`@venizia/vulcan`): `local: { tmp: 'tmp' }` moves the temporary files of a session to a short folder of the project, so a deep checkout no longer makes Chrome fail with `Socket path too long`. The default stays `.agents/local/tmp`. `vulcan sync` creates the folder, ignores it and points the Claude Code launch file at it, and `vulcan doctor` warns when the project path is too long for a browser socket.
- **The theme has presets, per-token colours and fonts** `theme-presets-and-tokens` (`@venizia/vulcan`): `theme.preset` is `venizia` (default) or `slate`, `theme.tokens` sets one token for both modes or for one, and `theme.font`, `theme.mono` and `theme.radius` set the type and corners; `accent` is no longer required. `vulcan sync` writes the resolved tokens to the manifest, and the board takes its colours and radius from them.
- **A visualize page takes grades, metrics and a muted title half** `visualize-grades-and-metrics` (`@venizia/vulcan`): `titleMuted` shows a second half of the headline, `grades` (1 to 12 items, grade `A`, `B` or `C`) are chips, and `metrics` (1 to 6 cards with a bar split by `parts`) are ratio cards.
- **`vulcan doctor` warns about private values in tracked files** `doctor-private-values` (`@venizia/vulcan`): a warning per file names a private key, a token, a password in a URL, an IP address or a machine path, with counts and never the value. Files that hold only addresses or machine paths are one line. A project that commits development credentials on purpose lists them in `doctor.privateValues.acknowledged`, each with a `reason`. The exit code does not change.
- **`changes` pages through a long window** `atlas-changes-pages` (`@venizia/vulcan-atlas`): when the entries of a window do not fit one reply, `changes` still answers `truncated: true` with the first page, and now also `nextOffset`; call again with `offset` set to it until it is absent to read the rest.
- **A version folder can carry a summary and highlights** `changelog-summary-and-highlights` (`@venizia/vulcan-atlas`): `summary` (one sentence) and `highlights` (a short list of one-line points) in the front matter of `log.md` say what the release is in a few words. `VersionFolders` reads both, and `vulcan changelog check --history` does not count an edit of either as a change to a released folder.
- **An upgrade can hold steps and the code** `upgrade-steps-with-code` (`@venizia/vulcan-atlas`, `@venizia/vulcan`): the `upgrade` of a block in `migration.yaml` may hold `steps` together with `before` and `after`, and `vulcan migrate plan` prints the code first and the numbered steps after it.
- **`knowledge.siteUrl` gives each `migrate plan` step a link to its upgrade guide** `migrate-plan-guide-link` (`@venizia/vulcan`, `@venizia/vulcan-atlas`): set it to the address of the project's wiki, and each step of a version folder prints `Guide: <siteUrl>/changelogs/<version>/upgrade#<id>`; a step of the JSON plan carries it as `guide`. Without it the plan prints no link.

## Changed
- **`guard-writes` asks for more commands and reads no scripts** `guard-writes-asks-for-table-commands` (`@venizia/vulcan`): the hook asks before the commands of its table (deploys, migrations, database writes, HTTP writers and the cloud, cluster and container CLIs such as `terraform`, `aws`, `gcloud`, `kubectl cp` and `exec`, `docker push`, `prisma migrate`) and before a command you list in `guard.writes.commands`, in every form the shell parser reads. It no longer opens `bun x.ts`, `node x.js`, `bash deploy.sh` or a package script, and a command it cannot read passes it; `guard-git` and `guard-outside` deny such a line and say how to write it again.
- **The guards deny a call they cannot read instead of asking you** `guards-deny-what-they-cannot-read` (`@venizia/vulcan`): a redirect to a word with an expansion the guard cannot work out (`> $f`), a program named by a variable and a line it cannot follow to its end used to stop the session for a person, almost always for a safe write under `.agents/local/tmp`. `guard-outside` and `guard-git` now deny such a call and the reason says how to write it again (a literal path, or the script in a file under `.agents/local/tmp/<task>/` run by its literal path, with literal paths in its own redirects), so the agent repairs it and you are not asked. `guard-outside` first works out the literal assignments of the same line (`S=.agents/local/tmp/x; ... > $S/a`, `export X=dir`, `for i in 1 2; do ... > f$i.log; done`); a value that points outside the project is still caught. A blanket `git add -A` past 50 paths and `gh pr create` with no `--base` are denied with their fix as well. Only what needs a person still asks: a plain force-push, `git reset --hard`, a force-delete of an unmerged branch, a push to a branch of `guard.git.askPush`, a write outside the project that was read, and a broken hook input or install. Nothing to do; the rule `V-B-08` now tells agents to keep scripts in files.
- **The board is three panes** `board-three-panes` (`@venizia/vulcan`): agents on the left, work items in the middle and the detail on the right, with a card that says where a flow is, what is happening and how far it got, and agent mascots. The Agent tab, the flow diagram, the Board columns view and the attempt rounds are removed. `board.agents` no longer hides any agent: the listed names come first and a `lane` is a label on the helper's own card. A flow shows the title of its `flow` line, and agent plumbing (session starts and stops, idle prompts) is hidden until you press Show all events. The page holds its words and not lookup keys. Write the board again with `vulcan board` to get it.
- **The event log stops writing a line for every turn** `event-log-quieter` (`@venizia/vulcan`): the Claude Code hooks no longer log a `session-stop` line at the end of a turn, so with `events.log` on the log shrinks to roughly half. Run `vulcan sync` to remove the `Stop` entry. The board treats an agent as working from a session start or any line it writes and idle after half an hour with none; old logs are read as before, and a `session-stop` line already in a log is still read.
- **A session with no name of its own is not an agent** `unnamed-sessions-are-not-agents` (`@venizia/vulcan`): a name Claude Code made from the folder, a counter or a clash is logged as `claude:<id>`, and the board makes no agent of it. Name a session (`/rename`, `--name`) to see it.
- **The rules reach the agent as a block of `AGENTS.md`** `rules-block-in-agents-md` (`@venizia/vulcan`): `vulcan sync` writes a `vulcan:rules` block of at most 6 KB (your slot choices, the write boundaries, where scratch goes, and the rules of `digest.oftenDropped`, one line each) next to the Atlas block, and the Claude Code session digest shrinks to under 2 KB and keeps only a config problem, a launch warning and the owner card. `vulcan doctor` notes a missing or stale block. Run `vulcan sync` and commit `AGENTS.md`.
- **Base rule wording is corrected** `base-rule-wording` (`@venizia/vulcan`): `V-C-09` says a comment states a lasting fact or is public-API TSDoc, and TSDoc is optional, written when it says what the name and types do not; `V-C-13` lets a project name an exception to a native docs site; `V-B-02` says the pre-commit hook is the project's own; the Enforced by cell of nine rules now says what holds, with `V-W-06` hard only for what `guard-git` reads; and `V-W-06`, `V-S-01`, `V-P-07`, `V-P-08`, `V-P-10` and others are shorter. `vulcan sync` reports each changed rule once.
- **The skills ask for a rules check and lose their evals** `skills-ask-for-a-rules-check` (`@venizia/vulcan`): `build-a-feature`, `review-a-change` and `ship` ask the agent to read the rules against the whole diff, name a rule id on each standards finding and put a Rules checked section in the pull request body; `base/templates/pull-request.md` holds the sections. The `evals/` folder of each shipped skill is no longer in the package, and `references/testing.md` lost its section on evals for skills and rules.
- **`vulcan doctor` prints fewer lines** `doctor-prints-less` (`@venizia/vulcan`): seven notes and warnings are removed (the app scripts note, the dockerignore, stray worktree, local size, reply shape and guard pattern notes, and the note on a trusted-script subcommand), and each stale leftover under `.agents/local/` and each entry VULCAN does not know there is no longer a line of its own: the leftovers are one warning with a count and the command that clears them, and the unknown entries are one warning with their names. The exit code and the `vulcan doctor: OK` line do not change; a script that parses stderr for one line per leftover reads the new line.
- **`vulcan init` ignores every env file** `init-ignores-env-files` (`@venizia/vulcan`): the `.gitignore` and `.dockerignore` it writes carry `**/.env`, `**/.env.*` and `!**/.env.example`, unless your own `.env` rule is already there. `.agents/local/agents/<name>/` is known to `vulcan doctor` as the home of one agent's own state, and `vulcan clean` never takes it.
- **The visualize pages take the Venizia look** `visualize-pages-take-the-venizia-look` (`@venizia/vulcan`): a page is dark by default with a light mode and an amber accent, stat tiles are divided cells, a heading has a label above it, and the default token values of the `venizia` preset change for every project. The board and the wiki read them from the manifest, so they move at the next `vulcan sync`; a project that sets its own `theme.tokens` keeps its values. Regenerate a page to get the new look.

## Fixed
- **`guard-outside` follows the links a line makes** `guard-outside-judges-links` (`@venizia/vulcan`): `ln ../victim h; echo x > h` and `ln -s ../victim s; echo x > s` wrote outside the project without a question, because the guard checked the name of the link and not the file it points at. It now denies an `ln` whose source is outside the project (a symbolic source is read from the folder of the link; `-t`, `-r` and a folder name are followed), and a path or a `cd` that goes through a link made earlier on the same line is not followed and is denied. The reason says to copy the file into the project or link a path inside it.
- **Two waiters of a dead pull lock can no longer both take it** `atlas-pull-lock-one-waiter` (`@venizia/vulcan-atlas`): when a pull died holding the lock, two atlas starts that found it at once could pull into the same cache together. Only one does now.
- **The commit-msg hook belongs to its project** `commit-hook-belongs-to-its-project` (`@venizia/vulcan`): `vulcan sync` writes the hook for one project and only touches a hook it wrote for its own folder, so a project inside another project's repository no longer removes or rewrites it; `vulcan doctor` says whose hook it is. A project folder whose name holds a control character gets no hook and a stated reason. Run `vulcan sync` once at the git top level to rewrite a hook an earlier release wrote below it.
- **The guards keep their settings when the config cannot be read** `guards-keep-settings-when-config-unreadable` (`@venizia/vulcan`): `vulcan sync` writes `guard.outside`, `guard.toolOwnedPaths` and the commands into the manifest, and the guards read it, so a config this release cannot parse no longer turns a deny into an ask. The session digest names the config problem. Run `vulcan sync` once after updating and commit the manifest; until then the guards use their defaults.
- **`atlas surface check` says when no public surface was committed** `surface-check-says-not-set-up` (`@venizia/vulcan-atlas`): a missing `public-surface.md` reads `not set up` with the command to run once, not `stale`. The exit code is still 1.
- **`symbol` finds the exports of a package that publishes its TypeScript source** `atlas-symbol-reads-source-packages` (`@venizia/vulcan-atlas`): in a repository, a package whose `exports` point at `.ts` files had no symbols; it is read now and follows an edit without a restart. A `.d.ts` entry still wins.
- **A visualize page holds its text** `visualize-figures-hold-their-text` (`@venizia/vulcan`): boxes and arrow labels are sized from their text, links of the architecture figure never cross a box and keep their distance, up to six boxes in a layer are drawn, step diagrams fit the page, the legend follows the page language (`chrome.nodeKinds` and `chrome.edgeVariants` override it), prose is set in the text font, the top bar shows whole links and keeps the theme switch on screen, the title has room for Vietnamese marks and a tile value stays off its state icon. Regenerate a page to get the fix.
- **`vulcan sync` keeps the contents list of `AGENTS.md` fresh** `sync-writes-the-agents-contents-list` (`@venizia/vulcan`, `@venizia/vulcan-okf`): when the Atlas and rules blocks take `AGENTS.md` past 100 lines, `okf check --strict` no longer fails after a sync, because `sync` writes the list itself. `@venizia/vulcan-okf` exports `ContentsList`.
- **A running atlas reads the installed version again when it changes** `atlas-symbols-follow-the-install` (`@venizia/vulcan-atlas`): a server answered `symbol` from the `@venizia/*` copy installed when it first answered and kept doing so after a bump, so a signature one release old was served until the server was restarted. It now looks at the installed copy before each question and reads the declarations again when the version or the folder moved.

## Security
- **atlas limits what it downloads and which transports git may use** `atlas-limits-and-git-transports` (`@venizia/vulcan`, `@venizia/vulcan-atlas`): the `repo` and `ref` of an `atlas.sources` entry are handed to git as plain values. atlas reads at most `atlas.limits.download` bytes of a tarball (1 MiB to 1 GiB, default 128 MiB), and git runs with only `https`, `ssh` and `file` allowed and never prompts. The values the config may no longer hold are in the Breaking item `atlas-config-values-refused`; a tarball over the limit needs a higher `atlas.limits.download` or a git read. A source that relied on a credential prompt fails, because git never prompts. Update `@venizia/vulcan` and `@venizia/vulcan-atlas` together, and upgrade before you set `atlas.limits`, which an older release refuses.
- **The board reads its logo only from inside the project and keeps its token out of the browser launch** `board-token-and-logo` (`@venizia/vulcan`): `board.logo` must be an `.svg` file that lies inside the project, links included, and a logo that fails is left out with a note. `vulcan board serve --open` gives the opener the path of a short-lived page in the project's tmp folder, not the address with the token.
- **The command guards read more forms of a command** `guards-read-more-command-forms` (`@venizia/vulcan`): `guard-git`, `guard-outside` and `guard-writes` share a shell parser that reads comments, arithmetic, multi-line quotes, heredocs, here-strings and a shell fed on its input the way bash does; `guard-git` and `guard-outside` ask when they cannot tell (a program named by a variable, a quote that never closes, a line over budget), and all three now ask when the hook input cannot be read, where they passed before (`guard-writes` passes a command it cannot read). `guard-outside` follows a link before a `..`, checks each branch of a brace list, reads `~name` as that user's home, uses a variable set earlier on the same line, and sees `>&file`, attached option values and options placed after the destination. `guard-git` reads the command a `find` runs and denies `gh api -X DELETE` on a protected branch, a call that passed before. The git queries of the guards run with the repository's fsmonitor, hooks and pager switched off and drop `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE`.
- **The redaction recognises more forms of a credential and is bounded in time** `redaction-covers-more-secrets` (`@venizia/vulcan`): the redaction of event text and the private-values check read one list that now catches a password on a command line, an `Authorization` header of any scheme, cookie values, DSN keys, Slack webhook paths, more token prefixes and a password in a URL that holds `/`, `@` or `:`. A `Bearer` credential is matched by its shape, so the words "Bearer authentication" in prose are left alone, and the time to read a long line grows with its length. A tracked file with one of the new forms gets a `private-values` warning it did not get before.
- **A project can make every guard refuse instead of ask, and the launch environment holds it** `guards-asks-deny` (`@venizia/vulcan`): `guard.asks: 'deny'` turns each answer that would ask a person into a refusal with the same reason, for agents that run in an auto mode, where an ask was approved with no person answering. It covers the commands of `guard-writes` and `guard.writes.commands`, a push to a branch of `guard.git.askPush`, `git push --mirror`, `git reset --hard`, a force-push to a branch that is not protected, a force-delete of an unmerged branch, a write outside the project, a hook input that could not be read, and a hook that crashed or timed out; omp, pi, Antigravity and Codex follow it. `VULCAN_GUARD_ASKS=deny` and `VULCAN_GUARD_OUTSIDE=deny` do the same from the environment that starts the agent, and the strictest of the environment and the manifest holds, so a project file cannot loosen it. A manifest that exists and cannot be read holds every ask. The default is `ask`; run `vulcan sync` after you set the key.
- **`guard-outside` denies a write to the files the guards read their policy from** `guards-protect-their-own-files` (`@venizia/vulcan`): an agent that could edit `.agents/vulcan.manifest.json`, `.configs/vulcan.config.*`, `.claude/settings.json`, `.claude/settings.local.json` or `node_modules/@venizia/vulcan` could switch a guard off, so a `Write`, `Edit`, `MultiEdit` or `NotebookEdit`, and in a Bash call a redirect, `tee`, `cp`, `mv`, `rm`, `ln`, `sed -i`, `perl -i`, `truncate` and the like, are refused whatever the project sets. The owner changes these files by hand or through `vulcan sync`; an agent can no longer edit `.configs/vulcan.config.*`. `bun install` and `bun node_modules/.bin/vulcan sync` are not writes the guard reads and still run.
- **`guard-git` and `guard-outside` block while the package or the hook is missing** `guards-block-a-missing-install` (`@venizia/vulcan`): a call used to run, with a note on stderr, when `node_modules/@venizia/vulcan`, `bun` or the hook file was missing, which is the state of a `bun install` that replaces the package. They now block with "VULCAN guards unavailable", as `guard-writes` does; `guard-git` only for a command that names `git` or `gh`. `bun install` and `bun node_modules/.bin/vulcan sync` still pass, so the install can be repaired from the same session. The wrapper is in `.claude/settings.json`: run `vulcan sync` and restart the session to get it.
- **A package run by name is refused, and what VULCAN writes runs the linked bin** `unscoped-runners-refused` (`@venizia/vulcan`): npm gives `vulcan`, `devz`, `ardor` and `ignis` to unrelated packages, and bun runs a copy an earlier bare bunx saved even under `--no-install`. `guard-git` now denies a command that runs an unscoped package through `bunx`, `pnpx`, `bun x`, `npx`, `npm exec`, `pnpm dlx` or `yarn dlx` (also behind `corepack` or `xargs`, and a runner with no name) in Claude Code, Codex, Antigravity, omp and pi (another agent has the new rule `V-S-08` only); a scoped package (`@scope/name`), a name in `guard.runners.allow` (with a version or a tag, not an `npm:` or `github:` spec) and the `--no-install` form pass, the last only for a bin linked in the folder the command runs in, with no flag other than `--bun` and `--silent`. What `vulcan sync` and `vulcan init` write no longer uses bunx: the `.mcp.json` atlas entry starts `bun node_modules/.bin/vulcan x atlas mcp --root .`, the commit-msg hook runs the linked bin by path, `make` runs `bun $(CURDIR)/node_modules/.bin/vulcan` (set `VULCAN` to change it), and the commands VULCAN prints say `bun node_modules/.bin/vulcan`. To upgrade: run `vulcan sync` once, which rewrites the old `.mcp.json` line and the hook it wrote; run `bun node_modules/.bin/vulcan runners check` and fix each line it lists (run `bun node_modules/.bin/<bin>` from the project root, or through a make target (`bun run <bin>` only as a fallback: it runs a program on `$PATH` or one bun cached when the bin is not linked), or add the name to `guard.runners.allow`: a project that runs `shadcn` adds `shadcn`); and change a hook of your own under `core.hooksPath` that still runs vulcan through `bunx` or `bun x` (`vulcan doctor` reports it as out of date). Then look in `~/.bun/install/cache/.bunx-*/` for an entry named `<name>@<version>` where the name is `vulcan`, `devz`, `ardor`, `ignis` or `vulcan-atlas`, and delete it.
