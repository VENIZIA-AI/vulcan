This release makes the guards catch more of what an agent can do: more ways to write or delete a file they protect, more ways to launch a package, and the package managers' ways of swapping in another `@venizia/vulcan`. If your project sets `BUN_OPTIONS`, `NODE_OPTIONS` or `BUN_CONFIG_*` in `claude.settings.env`, move them to your shell.

## Breaking
- **The config is in seven groups, and the flat shape is refused** `config-groups` (`@venizia/vulcan`): `.configs/vulcan.config.mts` has the groups `project` (`name`, `key`, `layout`, `packages`, `presets`), `agent` (`list`, `packs`, `rules`, `digest`, `owner`, `claude`), `guard`, `board` (`events`, `page`, `provider`), `knowledge` (its own keys, `okf`, `atlas`), `check` (`doctor`, `commit`, `layout`) and `common` (`theme`, `local`, `remove`), and the types `VulcanConfig.Project`, `.Agent`, `.Guard`, `.Board`, `.Knowledge`, `.Check` and `.Common`. A config in the flat shape of the earlier releases (`name`, `agents`, `rules`, `okf`, `events`, `local`...) is refused by every command, with the new path of each key (`events: moved to board.events`); only `vulcan migrate` and `vulcan config codemod` still read it, to move it. `vulcan config effective`, `vulcan config diff` and the doctor name a value by its group path (`agent.digest.oftenDropped[P-09]`, `board.page.title`), `common.remove` names its arrays the same way (`'knowledge.atlas.sources'`), and `vulcan config format` and the doctor order the keys inside each group. A group with a key it does not have is refused with the path of the key (`project.nme: not a key of project`), and `check.doctor.layout` is refused too: the layout check is `check.layout`. What to do: run `bun node_modules/.bin/vulcan config codemod config-groups . --write` (it lists what it would write without `--write`; `--split` makes one module per group under `.configs/vulcan/`), or `bun node_modules/.bin/vulcan migrate apply`, then review the diff and commit. A module typed `VulcanConfig['claude']`, `['doctor']`, `['okf']` or `['packages']` (the modules `vulcan project init` wrote in 0.5.0-7 and -8) is retyped by the codemod. Your own machine's profile is moved by `vulcan project sync` (see the entry on the profile keys).
- **The config names `type`, `presetType` and `types`, not `kind`, `presetKind` and `kinds`** `type-names` (`@venizia/vulcan`, `@venizia/vulcan-atlas`): the entries of `project.packages` (and the `vulcan:apps` block `vulcan package add` writes) say `type: 'lib'` and `presetType: 'shared'`, and an acknowledgement of `check.doctor.privateValues.acknowledged` says `types: ['ipv4']`; the config schema, the manifest `vulcan project sync` renders and the atlas `presets` tool read the new names, and the old ones are refused. The constants are `PackageTypes` and `LibraryTypes`. What to do: run `bun node_modules/.bin/vulcan config codemod type-names . --write` (or `bun node_modules/.bin/vulcan migrate apply`), which renames the keys in the config, its modules and the apps block, then run `bun node_modules/.bin/vulcan project sync`.
- **An event line has `type`, and `vulcan event add` takes `--type`** `event-type-field` (`@venizia/vulcan`): the field that said `kind` in every line of the event log is `type`, and the flag `--kind` is `--type`. `vulcan project sync` moves the lines of the day files of the log once and says how many; nothing reads `kind` afterwards. What to do: run `bun node_modules/.bin/vulcan project sync`, and change any script that runs `event add --kind` or reads the `kind` field of a line.
- **The atlas answers without `kind`** `atlas-field-names` (`@venizia/vulcan-atlas`): the `presets` tool takes and answers `type`, the symbol records (`symbol`, `search`, the surface lines) carry `category`, a `changes` entry carries `badge` (the text of its first badge) and the `touches` of a `migrate` plan carry `reach`; the index format is 3, so the stored sets are rebuilt. What to do: change the scripts and agent text that read those fields, and run `bun node_modules/.bin/vulcan atlas pull`.
- **A page spec says `type`, not `kind`, on a node, a message and a state** `visualize-type-field` (`@venizia/vulcan`): `vulcan page new` reads `type` where the spec had `kind`, and refuses `kind` naming it. What to do: rename the key in the spec files you keep.
- **The hooks drop the loader variables** `launch-file-and-loader-variables` (`@venizia/vulcan`): the hooks remove `BUN_OPTIONS`, `NODE_OPTIONS` and `BUN_CONFIG_*` from their environment, and `vulcan project sync` refuses them in `claude.settings.env`. What to do: if you set one of them in `claude.settings.env`, move it to your shell; `vulcan project sync` tells you which.
- **`.agents/vulcan.local.json` is gone: its keys live in `.agents/local/profile.json`** `local-json-folds-into-profile` (`@venizia/vulcan`): the agents you chose, your own `board.agents`, `board.serve.autoStart`, `local.tmp` and `events.dir` are now keys of the one per-person file, `.agents/local/profile.json`, next to your profile (`vulcan profile` keeps them when it saves your answers and `vulcan profile reset` removes only the answers). `vulcan project sync` moves the keys of the old file into the profile (a key the profile already has keeps its value, and the note names it) and deletes the old file when git does not track it; if git tracks it, the keys are moved first and the note says to run `git rm --cached .agents/vulcan.local.json` and delete the file; a key the profile does not take (a typo) stays in the old file, which stays too, and the note names it. Until sync has run, the hooks and `sync` still read the old file. The profile file is protected from an agent's writes like the old one. An unknown key in the profile is now refused by `vulcan project doctor` (the profile is strict). What to do: run `vulcan project sync`; a script that reads or writes `.agents/vulcan.local.json` uses `.agents/local/profile.json`.
- **The default scratch folder is `.agents/tmp`** `tmp-default-agents-tmp` (`@venizia/vulcan`): scratch files, `TMPDIR` of the session, the board log and `vulcan project clean` use `.agents/tmp` instead of `.agents/local/tmp`: a shorter path (a browser's socket path fits in more checkouts, so a project that set `local.tmp: 'tmp'` only for that can drop it), outside `.agents/local/`. `vulcan project sync` makes the folder and adds `/.agents/tmp/` to a committed `.gitignore` (unless a line there already ignores `.agents/`), and `vulcan project init` writes `.agents/tmp/` into the `.gitignore` of a new project; `local.tmp` still replaces it. An old `.agents/local/tmp` is left alone, and `vulcan project clean` lists and removes its old items like the new folder's. Rule V-B-08 names the new folder. What to do: run `vulcan project sync`; a script, Makefile, workflow or doc that names `.agents/local/tmp` names `.agents/tmp`; remove the old folder when it is empty (`vulcan project clean --tmp --yes` takes what is stale).
- **Every command is `vulcan <scope> <action>`** `command-scopes` (`@venizia/vulcan`): `project` (init, sync, doctor, upgrade, clean), `package` (add, diff), `agent` (list, add, remove, setup), `config` (effective, diff, format), `check` (commit, runners, changelog, layout), `migrate` (plan, apply, notes), `flow` (add, step), `event` (add, tail), `board` (show, serve), `page` (new, schema), `profile`, `okf` and `atlas`. The old top-level names (`vulcan sync`, `vulcan doctor`, `vulcan init`, `vulcan add`, `vulcan x atlas`, `vulcan commit-check`, `vulcan board`, `vulcan visualize`...) print the new form on stderr and exit 2. `vulcan sync`, `vulcan commit-check` and `vulcan x` still run in this release, with the same notice, because the `prepare` script, the commit-msg hook and the `.mcp.json` entry of a project call them before anyone has run `vulcan project sync` once; they go in the next release. What to do: run `bun node_modules/.bin/vulcan project sync` once (it rewrites the hook and the `.mcp.json` entry), then use the new names in your scripts, Makefiles, workflows and docs. `make lint-all` of this repository fails on a retired name.
- **Claude Code's settings are never committed, and `bun install` writes them** `claude-settings-never-committed` (`@venizia/vulcan`): `.claude/settings.json` is written by `vulcan project sync` in every clone, so `sync` adds `/.claude/settings.json` to a committed `.gitignore` that does not already ignore `.claude/`, and `vulcan project doctor` warns when git tracks it (run `git rm --cached .claude/settings.json`). `vulcan project init --preset` writes a `prepare` script into the root `package.json` so `bun install` runs `vulcan project sync --quiet` (guarded: it does nothing when vulcan is not installed, notes a failing sync, exits 0 and reads no terminal); `vulcan project init` in an existing directory leaves your `package.json` alone, and `vulcan project doctor` notes a project with no such script and prints the line. `vulcan project sync --quiet` prints only what changed. The first lines of the rules block in `AGENTS.md` now say: run `vulcan project sync` (`bun install` runs it when the `package.json` has the `prepare` script) before you work; until then no guard is active. A machine with no stored choice of agents and no terminal takes `claude`; users of Codex, omp or pi run `vulcan project sync --agents <list>` once. The script is POSIX `sh`: Windows is untested. What to do: `git rm --cached .claude/settings.json` if git tracks it, add the `prepare` script, and run `vulcan project sync` in CI before any step that reads the manifest.
- **The manifest is split: the hooks' part is local, atlas's part is committed** `manifest-local-and-descriptor` (`@venizia/vulcan`, `@venizia/vulcan-atlas`): `vulcan project sync` now writes `.agents/local/vulcan.manifest.json` (the whole manifest, gitignored, one per clone: the hooks, the board and `vulcan project doctor` read it) and, in a repository that publishes (its config sets `atlas.index.keys`, or git already tracks `.agents/atlas.manifest.json`), `.agents/atlas.manifest.json` (name, packages, layout, presets, knowledge, release, sources, atlas and the resolved theme: committed, generated). An app, which publishes nothing, gets no descriptor and no copy: everything stays in the local manifest, and atlas reads its own project from there; `vulcan project sync` deletes a descriptor or a copy left untracked by an earlier sync and never touches a tracked one, or one git cannot tell about (that repository counts as publishing). A new atlas source that signs nothing commits its descriptor once: set `atlas.index.keys`, run `vulcan project sync`, and commit `.agents/atlas.manifest.json`; from then on git tracking it keeps `sync` writing it, keys or not. `.agents/vulcan.manifest.json` is no longer read by the hooks; `vulcan project sync` keeps it as a data-only copy of the descriptor, committed, until the stable 0.5.0 release, because atlas of 0.5.0-6 and before reads a source's manifest only at that path and needs it to resolve the source's ref before it can pin a release tag (without it `vulcan migrate plan` and the `vulcan` source fail with `has no .agents/vulcan.manifest.json`). A newer atlas reads the descriptor first; the copy goes with the stable release. `vulcan project doctor` names a missing or stale copy. A fresh clone, and a clone just upgraded, has no local manifest until `vulcan project sync` runs: until then every ask is a deny and every write outside the project is refused (the same hold as an unreadable manifest), agent signatures in a commit message are refused, and the session digest says to run `vulcan project sync`, a command that passes the guards. What to do: in an app, run `vulcan project sync`; an app that tracks the descriptor from an earlier release keeps it written (it reads as a source), and you may `git rm --cached` both files if no project reads it through atlas. In a repository that publishes, run `vulcan project sync` and commit `.agents/atlas.manifest.json` and the copy `.agents/vulcan.manifest.json` (keep it tracked; its content is now the descriptor, not the old manifest), point your wiki config at the new file (a repository that copies the shared wiki theme takes the new `changelog-prereleases.ts` too), and run `vulcan project sync` in CI before the tests and the gates.
- **The Claude Code launch file is gone** `claude-launch-file-dropped` (`@venizia/vulcan`): `vulcan project sync` no longer writes `.agents/local/claude.launch.settings.json`, and the doctor note and the session-start launch warning that asked you to start Claude Code with it are removed; `sync` deletes a leftover the project's git does not track. The session start still sets `TMPDIR` for every command the agent runs, and now tells the agent to keep scratch there and not in the scratchpad Claude Code offers in /tmp, which `guard-outside` refuses. What to do: start Claude Code without `--settings .agents/local/claude.launch.settings.json`; to keep Claude Code's own temp files in the project, export `CLAUDE_CODE_TMPDIR` in your shell. `vulcan project doctor` now warns about a browser socket that is too deep for every project, not only one that had the launch file.
- **The guards read more ways to write or delete a protected file** `guards-read-more-write-forms` (`@venizia/vulcan`): these are now protected like the project settings: a copy, a move, an install, a link or an extraction into the folder of a protected file; a pattern, `find -delete` or `git clean -x` that can reach one; an edit in place; and the files the agent integrations write for Codex, Antigravity, omp and pi (`.codex/hooks.json`, `.agents/hooks.json`, `.omp/hooks/pre/vulcan-guards.ts`, `.pi/extensions/vulcan-guards.ts`). `sed -i`, `perl -pi`, `truncate`, `tar`, `unzip` and `git init` outside the project now ask first, like any other write. What to do: if you extract an archive at the project root (`tar xf`, `unzip`) or clear `.agents/local/*`, use a subfolder instead (`tar xf a.tar -C dist`, `.agents/tmp/*`).
- **A package run through more launchers is refused like `bunx`** `guards-read-more-launchers` (`@venizia/vulcan`): the guards now refuse a package run through `taskset`, `flock`, `runuser`, `parallel`, `su -c`, `script -c` or `find -exec sh -c`, and also `bun create`, `npm init` with a package name, `npm create`, `pnpm create`, `yarn create` and `bun add -g`. `make runners-check` now finds the same forms in your docs or scripts, as it does for `bunx`: a `bun create`, an `npm init` with a package name, an `npm`, `pnpm` or `yarn` `create` and a `bun add -g`. What to do: add the package to the project's dependencies and run its bin from `node_modules/.bin`, or list it in `guard.runners.allow` (for a scaffolder such as `vite`, the name goes there).
- **A commit or a pull request needs a flow in a project that logs events** `flow-required-for-commit` (`@venizia/vulcan`): with `events.log` on and a `project.key` set, the git guard refuses `git commit`, `gh pr create` and `glab mr create` when no flow can be found, and prints the `vulcan flow add` command that makes one. A flow is found from the branch name, a `Flow: <id>` in the command, or the flow the session last opened. Projects with `events.log` off are not affected, and neither is a project with no `project.key` (it cannot make a flow, so it is not refused: set the key and run `vulcan project sync` to turn the rule on). Make the flow first and name the branch with its id.
- **`digest.oftenDropped` adds to the shipped list instead of replacing it** `digest-add-replaces-often-dropped` (`@venizia/vulcan`): the ids a project lists are now added after the 11 ids VULCAN ships (`base/defaults.config.json`), as every array of the shipped layers is; a project that had put the ids in its own order loses that order, because the shipped ids come first. A project that listed fewer ids than the default used to drop the rest; to keep that, take the ids out with `remove: { 'digest.oftenDropped': [...] }`.
- **VULCAN ships a read-only allow list, and the venizia pack ships the stack's config** `config-defaults-from-base-and-pack` (`@venizia/vulcan`): every project now gets, in `.claude/settings.json` after `vulcan project sync`, 42 allow lines for commands that only read (`ls`, `grep`, `jq`, `rg`, `git log`, `git diff`...) with 14 companion denies for flags that write a file or name a program (`date -s`, `rg --pre`, `git ... --output`, `git cat-file --filters`...). A shipped deny can refuse a command one of your own allow lines used to permit: take it out with `remove: { 'claude.settings.permissions.deny': [...] }`. A project with `packs: ['venizia']` also gets the presets `ignis` and `ardor`, the atlas sources `ignis`, `ardor` and `vulcan`, and five allow lines for `bun run typecheck|test|lint`, `bun test` and `bun check`. A standing `**/Dockerfile*` acknowledgement for container paths comes with the base. This loosens the permissions of every project on upgrade: run `vulcan config effective` to see the result, `vulcan config diff` to see which lines you wrote that are now repeated, and take out what you do not want with `remove`.
- **The venizia pack refuses writes outside the project and agent signatures by default** `pack-guard-and-commit-defaults` (`@venizia/vulcan`): a project with `packs: ['venizia']` now gets `guard.outside: 'deny'` and `commit.message.agent.signature: 'deny'` without writing them. A project that wants the earlier behaviour writes `guard: { outside: 'ask' }` and `commit: { message: { agent: { signature: 'allow' } } }`; a project that already wrote the same values can delete them (`vulcan config diff` lists them, and `vulcan project doctor` notes how many repeat the defaults). `vulcan project doctor` also warns about a `remove` entry that matches nothing. What to do: run `vulcan project sync` and commit what git tracks that it changed, `.agents/atlas.manifest.json` and, where the project commits it, `.claude/settings.json` (with the signature denied, sync blanks the attribution Claude Code adds to a commit and a pull request); every clone runs `vulcan project sync` once to install the commit-msg hook. Plan mode of Claude Code still writes its plan file under `~/.claude/plans` or `$CLAUDE_CONFIG_DIR/plans`: those folders are allowed as tool-owned paths.

- **Const classes lose `SCHEME_SET` and share a base, `ConstClass`** `const-classes-extend-const-class` (`@venizia/vulcan-atlas`, `@venizia/vulcan-okf`): the classes of the two packages that listed their values in a `SCHEME_SET` set (atlas: `Corpora`, `AtlasCommands`, `SkillSources`, `PackageKinds`, `LibraryKinds`, `AppSides`, `SourcePins`, `LogLevels`; okf: `ConceptStatuses`, `IssueSeverities`, `ReservedFiles`) now extend `ConstClass`. `X.SCHEME_SET` is gone; `X.values()` returns the values as a list and `X.isValid(value)` checks one and narrows its type. What to do: replace `X.SCHEME_SET.has(v)` with `X.isValid(v)` and `[...X.SCHEME_SET]` or a loop over it with `X.values()`.
- **`vulcan page new` pages are simpler, and the spec changes with them** `visualize-pages-simplified` (`@venizia/vulcan`): a page is one light column with a head, a contents line, your actions, the decisions, the steps and the background, in that order, and it has no dark top slab, no dark footer and no kicker labels. A decision is a question that ends with `?`, two or three options with exactly one recommended, and a reason (`question`, `options`, `why`, `detail`); a step name is at most 40 characters and its note 80; a title is at most 60; a written section takes typed blocks (`sections`). A spec is now refused if it has `titleMuted`, `tiles`, `caption` or `language`, a title over 60 characters, a decision with `recommended` and `changes`, or a code-like question or option label. The page language is the owner profile's language, else English. A page for the owner (steps, actions or decisions) has no Present button.

## Added
- **`make conflict-markers-check` fails on a git conflict marker in a tracked file** `conflict-markers-check` (`@venizia/vulcan`): a merge committed with a marker left in a document passed every gate. The new target of `vulcan.mk` reads every tracked file and fails on `<<<<<<<`, `|||||||` or `>>>>>>>` at the start of a line, or a line that is exactly `=======`. `make wiki-links-check` runs it first, so a project that runs that gate gets it with the upgrade. What to do: nothing; if a file holds such a line on purpose, set `CONFLICT_MARKERS_FLAGS='--skip <path prefix>'`, and remove any target of your own with the same name.
- **`vulcan config codemod config-groups` moves a config into the groups** `config-codemod` (`@venizia/vulcan`): it rewrites `.configs/vulcan.config.mts` from the flat shape into the seven groups with every value, comment and import kept, with `--split` into one module per group under `.configs/vulcan/` (folding in the modules a 0.5.0-7 or -8 split has, and deleting only those, only under `.configs/vulcan/`), a monorepo's `vulcan:apps` block moves to `.configs/vulcan/project.mts`, and it lists what it would write unless it is given `--write`. There is no way back: restore the earlier config from git. It also rewrites the types of those modules (`VulcanConfig['claude']` is `VulcanConfig.Agent['claude']`). A config it cannot move without losing something (a spread, a computed key, a statement before the export when splitting, a module with more than its one value, a file already in the way) is refused with the reason and nothing written. The guards deny, for an agent, every `vulcan` command that writes the config: `config format` without `--check` and `config codemod ... --write`. What to do: run it on the config of each project before the release that refuses the flat shape.
- **The machine keys of `.agents/local/profile.json` follow the groups** `profile-keys-in-groups` (`@venizia/vulcan`): `agents` is `agent.list`, `board.agents` is `board.page.agents`, `events` is `board.events` and `local` is `common.local`; `board.serve.autoStart` stays. The first `vulcan project sync` after the upgrade (`bun install` runs it) moves each key in place, once: a value already at the new path stays and is named, a key it cannot place stays where it is and is named, and `--dry-run` lists the move without writing. `.agents/vulcan.local.json` is moved into the new paths the same way. Until it has run, a command that reads the profile refuses the old key and names its new path. What to do: nothing; run `vulcan project sync` if a command tells you to.
- **The `venizia` rule pack names a class by what it is** `rule-v-c-21` (`@venizia/vulcan`): the new rule `V-C-21` gives every class a name that tells you what it is. An object you create or bind that holds state is a `XxxHelper`, in `helpers/`, extending `BaseHelper`. Every other class is static: an access point to one thing is named after it with no suffix (`RuntimeConfig`, `AppEnv`), a bag of pure functions is a `XxxUtility` in `utilities/`, a class with a clear role is named for it (`Reader`, `Builder`, `Encoder`, `Factory`, `Registry`, `Store`, `Guard`), and a class of constants is named for its group (`HTTP`, `RequestTypes`). One protocol keeps one constants namespace and one class prefix. What to do: nothing, unless your project lists `packs: ['venizia']`; then run `vulcan project sync` to receive the rule.
- **Atlas answers from the last good index at once, and says how far a source has got** `atlas-serves-last-good-index` (`@venizia/vulcan-atlas`, `@venizia/vulcan`): the server records each source it built in `.agents/local/cache/atlas/status.json` and, on the next start, serves it from that index immediately while a child checks the remote; the fresh index replaces it in place, and a remote that is down no longer takes a source away. An older index is served only while it is still what a fresh start would serve: the same source, a complete set of this atlas's index format, and, for docs pinned to the installed version, the same tag the installed packages decide now; after `bun update` or an atlas upgrade the source is built from nothing. `vulcan migrate` and `vulcan atlas tools` always wait for the fresh build. The `notServed` notice changed shape and wording: its `message` now opens with `N of M sources are ready` (the project counted on both sides) and names each source that is building (seconds so far, the usual time, when to ask again), served from an older commit or tag while it refreshes, or not refreshable; new fields `ready`, `building`, `stale` and `retryInSeconds` carry the same, so the warning `vulcan migrate` prints for an unserved source reads differently. `vulcan atlas status` prints the record (exit 1 on a source never served or a build hung in a live server) and `vulcan project doctor` warns about the same and about a failed refresh. What to do: nothing. The first start of a source with nothing recorded builds as before (and so does the first start after this release); later starts answer at once.
- **`vulcan page new` draws more kinds of chart and chooses the form from the data** `visualize-charts-chosen-from-data` (`@venizia/vulcan`): findings take `stack` (parts across groups), `meter` (value against a limit), `table` (exact values) and a `trend` line on a number. A `bar` of three values or fewer is a stat line, one over dates is a line, names are ranked bars and a negative value draws bars around zero; a `donut` is one segmented bar up to five parts and ranked bars beyond, and is never a ring; a `line` can mark one series with `emphasis`; a list of more than eight short items takes two columns. The label under a number tile is now sentence case at 13 px, not small capitals. Charts may now have up to 5 series, 12 parts and 6 charts per page. Specs that worked keep working.
- **You can set `board.agents` and `local.tmp` for your own checkout** `local-board-agents-and-tmp` (`@venizia/vulcan`): a team project no longer has to commit a personal board roster or a short temporary folder. Add `board.agents` and `local.tmp` to your gitignored `.agents/local/profile.json`, in the same shape as in the config, and they replace the committed value of the same key on your machine: the board page, the guards and `vulcan project clean` use them, while `AGENTS.md` and the manifest still hold the team's values only. `vulcan project sync` keeps these keys when it writes your agents and lists a local `tmp` folder in `.git/info/exclude`, `vulcan project doctor` names the file and key of a value it cannot use, and the file is now protected from an agent's writes.
- **You can set `events.dir` for your own checkout** `local-events-dir` (`@venizia/vulcan`): a shared event folder for a coordinator (a hub session above several repositories) is a path of one machine, which no longer has to be committed. Put `"events": { "dir": "/absolute/path" }` in your gitignored `.agents/local/profile.json`: it replaces `events.dir` of the config on your machine, for the hooks, `vulcan event`, `vulcan board show`, `vulcan project clean --events`, the token meter and the guards, while the manifest and every committed file stay as they are. A value that is not an absolute path is not used by the hooks and the other readers (the committed folder applies), `vulcan project sync` refuses until it is fixed, and `vulcan project sync` and `vulcan project doctor` name the file and the key. A linked worktree or a clone has its own file. `events.log` stays in the committed config.
- **`vulcan flow step` changes one step of a flow, and a Claude Code task list fills the steps** `event-step-and-todo-mirror` (`@venizia/vulcan`): `vulcan flow step --flow <id> --done "<step>"` (or `--todo`, `--next`, `--context`) updates a flow without restating its lists; it copies the flow's last line whole and writes it again with the change. In a project with `events.log` on, the `TodoWrite` list of a Claude Code session is merged into the steps of the flow the branch or the session last opened and that is not over: new tasks are added, completed ones are marked done, and nothing is removed or reopened, so an agent that keeps a task list needs no second step to keep the board true. A subagent's list is ignored. The hook reads only the text and the state of each task, cleaned and redacted.
- **The board shows a session with a running subagent as working** `subagent-start-signal` (`@venizia/vulcan`): with `events.log` on, `vulcan project sync` adds a `SubagentStart` hook that writes a `subagent-start` line (the agent type and id, nothing else), so a long subagent no longer leaves its session looking idle. `vulcan event add --kind` accepts `subagent-start`. What to do: run `vulcan project sync` and commit `.claude/settings.json`.
- **A turn that a user prompt starts begins with the flow and its open steps** `prompt-context-hook` (`@venizia/vulcan`): with `events.log` on, `vulcan project sync` adds a `UserPromptSubmit` hook that tells the agent the flow it works on, up to five open steps and the exact `vulcan flow step` command. It reaches only turns that a user prompt starts; a turn a peer message starts is still covered by the Stop hold. What to do: run `vulcan project sync` and commit `.claude/settings.json`.
- **The board can start with the session, on your machine** `board-serve-autostart` (`@venizia/vulcan`): `board.serve.autoStart: true` in your own `.agents/local/profile.json` makes the `SessionStart` hook start `vulcan board serve --port 4317` when the event log is on and no VULCAN board answers there; another program on the port is left alone. An explicit `--port` of `vulcan board serve` is now strict: a busy port is an error (`board: cannot serve`) and no longer a fallback to another port. The output, with the address and its token, goes to `.agents/tmp/board-serve.log`. What to do: nothing, unless you want it; a script that relied on the fallback with `--port` drops the flag.
- **A flow left with open steps for two hours is raised once** `stale-flow-reminder` (`@venizia/vulcan`): the Stop hook of a project with `events.log` on holds a turn once when the session's flow has open steps and no line of work for two hours, with the exact `vulcan flow step` commands, and then leaves the session alone for two hours. What to do: nothing; tick what is done, or say what comes next.
- **A Claude Code turn cannot end with the board out of step** `board-stop-hook` (`@venizia/vulcan`): in a project with `events.log` on, `vulcan project sync` installs a `Stop` hook. When the session committed, opened a pull request, edited tracked files (when it already has a line in the flow) or merged a pull request of the flow and the flow has no newer line, it holds the end of the turn once and prints the exact `vulcan flow step` command to run, with the open steps ready to tick. - **The board shows the tokens a flow used** `board-token-usage` (`@venizia/vulcan`): in a project with `events.log` on, the `Stop` and `SubagentStop` hooks of Claude Code write `usage` lines: the input, output, cache read and cache write tokens of a session and of its subagents, with the model and the agent, on the flow they worked on (or on none). `vulcan board show` adds them up per flow and shows a row for each agent and model. Codex, Antigravity, omp and pi are not covered.

Filters for the agent, the repository and the state, and a **Stale** switch, narrow every view the same way. Your view and the table's sort are kept in the browser, like your language and theme.
- **The config can come from shipped defaults, and `vulcan config` shows it** `config-layers` (`@venizia/vulcan`): the config the commands read is now the shipped defaults (`base/defaults.config.json`), then the config of each rule pack in `packs` (`base/packs/<name>.config.json`), then your file, merged as data: objects by key, arrays add, scalars are overridden by the later layer. A new `remove` key in your file takes items out of an array a shipped layer added, such as `atlas.sources`. `vulcan config effective` prints the merged config with the layer each value came from, and `--diff` lists the values your file repeats from a shipped layer. This release ships both files empty, so no project changes; the defaults that move in later are announced as they land.
- **`vulcan config format` puts the keys of your config in one order** `config-format` (`@venizia/vulcan`, `@venizia/vulcan-atlas`): the command rewrites `.configs/vulcan.config.mts` so its top-level keys come in the same order in every project: `name`, `project`; `agents`, `packs`, `rules`, `digest`, `owner`; `layout`, `packages`, `presets`; `guard`, `commit`; `events`, `board`; `knowledge`, `okf`, `atlas`; `claude`, `doctor`, `local`, `theme`; a key not in the list after them; `remove` last; a file written in the seven groups has the groups in order and, inside each group, its keys (the order is in the reference of `vulcan config`). Each key moves with its comments; the imports, the code before the export and every value stay as they are, and a file in order is not touched. It reads the file with TypeScript and never runs it, so it refuses (exit `2`, with the reason) a config with a spread or a computed key. `--check` writes nothing and exits `1` with the keys that would move, for CI, and `vulcan project doctor` notes the same as `config-order`. Atlas now exports `TypeScriptCompiler`, the loader the command reads the file with.
- **`vulcan check layout` finds plural file roles, mixed folders and long files** `layout-check` (`@venizia/vulcan`): the command reads the source files git tracks in your package and layout folders (else every `src` folder) and lists three kinds of finding: `plural-suffix`, a file name whose role is plural (`user.helpers.ts`, with the singular to use); `mixed-folder`, a folder with three or more subfolders and loose source files other than `index.ts` beside them; `long-file`, a source file over 400 lines that is not generated (a header that says generated or do not edit, or a glob you list). Set the limits in `doctor.layout` (`maxLines`, `minSubfolders`, `pluralAllow`, `generated`). To adopt it in a project that has findings, run `vulcan check layout --write-baseline` and commit `.configs/layout-baseline.json`: what it holds is then info, and only a new finding warns. `vulcan project doctor` warns with one line per rule as `file-layout`. Nothing to do unless you want the check: it never fails the doctor.
- **`vulcan project init` writes the config split into modules** `config-split-scaffold` (`@venizia/vulcan`): a new project gets `.configs/vulcan.config.mts`, which composes the seven groups, and one module per group in `.configs/vulcan/` (`project.mts`, `agent.mts`, `guard.mts`, `board.mts`, `knowledge.mts`, `check.mts`, `common.mts`, each one `satisfies` its group type), re-exported by `.configs/vulcan/index.mts`. The config loads as before, `vulcan config format` orders it, and the guards protect every module. A `packages` that is `undefined` now counts as not written, so the packages are derived from the workspaces, as when the key is left out. `vulcan project init --preset` writes the same modules, with the apps block in `project.mts`; `vulcan package add` and `package diff` find the block there or in the config file. Nothing to do in an existing project: one file stays valid, and splitting it is up to you.
- **A flow has a place in the work order** `board-flow-order` (`@venizia/vulcan`): `vulcan flow add --order <n>` and `vulcan flow step --order <n>` give a flow a positive whole number, and `--order none` clears it (the last value wins when it is repeated; `none` on `flow add` needs `--flow` of a flow that exists). A `flow` line may carry an `order`, written `null` when cleared; a line without one keeps the earlier order, so a retitle does not lose it, and a log with none stays valid. The board's Work items table has an **Order** column and starts with the active flows by order, a flow with none last, then the parked and done flows by order; flows that tie come with the ones that need you first, then the latest update. The cards and the compact lines show the number small, before the code. What to do: nothing; a project that listed the table's columns in its own tests expects one more, `Order`, first.

After each codemod that ran, `apply` now stages what it wrote (`git add -A`) and leaves the result staged: review it with `git diff --staged`; the steps that stay manual come after it. The app must still be clean at the start (nothing unstaged, staged or untracked), as before; a forced run over a tree with changes of its own stages nothing. What to do: nothing; rerun `apply`.
- **The "All events" list of a flow's details wraps its text in the full width** `board-all-events-text-width` (`@venizia/vulcan`): each summary was squeezed into a 14 pixel column, so it broke one word per line and painted over the rows below it. The summary now takes the width of the pane and the height its text needs.
- **`vulcan project doctor` no longer takes numbers in SVG path data for IPv4 addresses** `ipv4-standalone` (`@venizia/vulcan`): the `ipv4` kind of the `private-values` warning now counts an address only when it stands on its own, with no letter, digit, `_`, `.`, `-` or `,` touching either end. Compact path data such as `M1.2.3.4` or `c0.5.25.25.5` in an icon no longer warns; `10.0.0.1`, `192.168.1.10` and `host:10.0.0.1:8080` still do. If you acknowledged a file in `doctor.privateValues.acknowledged` only for such a false hit, the doctor now says the entry matches nothing: delete it.
- **The board table shows the whole flow id in the Code column** `board-table-code-column-fits-id` (`@venizia/vulcan`): the column was a fixed 120 pixels wide and cut an id of three digits, so `VULZ-BANA-140`, `-166` and `-175` all read `VULZ-BANA-1…`. The column is now wide enough for an id of 16 characters, such as `VULZ-VULCAN-1234`, the other columns keep their fixed widths, the cell carries the full id as its title, and at phone width the table scrolls inside its own frame.
- **A title-only `flow` line no longer empties the steps** `flow-line-keeps-steps` (`@venizia/vulcan`): after a flow had steps, two `flow` lines with only a title made `vulcan flow step --todo "new"` write a list of one step, and the board showed no steps. A `flow` line with no `--step` now keeps the list of the newest line before it that has steps, for `flow step`, the `TodoWrite` mirror, the Stop hook, the prompt context and the board; only a line that carries steps replaces the list. The writer never writes an empty list, so a log written before this release is read the same way: an old title-only line keeps the steps too. A flow cannot be emptied of steps by a line with none.
- **`changelog check` finds the codemod runner of a workspace package, and fails when it cannot check the names** `check-resolves-workspace-codemod-bin` (`@venizia/vulcan-atlas`): a repository that publishes its own runner (`knowledge.codemodCommand: ['ardor', 'codemod']`, the bin of one of its `project.packages`) has no `node_modules/.bin/ardor`, so the check said the command was not available and exited `0` with the codemod names unchecked. With no bin in `node_modules/.bin`, the check now reads the `bin` of the declared packages' own `package.json`; the file must lie inside that package folder, every link resolved, and it runs with the runtime that runs the check. It exits `1` when the names cannot be asked (not found, not built, outside the package, or `--list` fails) and the config sets `knowledge.codemodCommand` or an item names a codemod. What to do: if the bin is a built file, build the package before the check, in CI too; with a codemod named and no runner installed, install it.

## Security
- **The guards protect the modules of a split config** `config-modules-protected` (`@venizia/vulcan`): a config split into modules (`.configs/vulcan.config.mts` importing `.configs/vulcan/*.mts`) could be changed through a module: an agent could edit `.configs/vulcan/claude.mts` to widen the permissions allow list, or `doctor.mts` to exempt files from the private-values check, because only `.configs/vulcan.config.*` was protected. `guard-outside` now denies a write to anything under `.configs/vulcan/`, and to every other file under `.configs/` the config imports (`vulcan project sync` reads the imports with the TypeScript pre-processor and records them as `guard.configModules` in the local manifest), by the file tools, a redirect, `rm`, `mv`, a pattern, a `find -name` or a folder removal, like the config itself; a module is recorded by its path and by the real path of a link, and an alias of the root `tsconfig.json` `paths` or `package.json` `imports` is followed. A module the config reaches outside `.configs/`, a link that leads out (the config file included), a package of this repository (a workspace member, a `file:` or `link:` dependency), a specifier that names nothing the project has, or a file that cannot be read is not protected: `vulcan project sync` warns about it, and so does `vulcan project doctor` (`config-modules`); a module reached through an alias is named too, with `import it by a relative path`. A type-only import is not followed. What to do: run `vulcan project sync`; move any module it names under `.configs/`.
- **The guards refuse a package manager's way of swapping in another `@venizia/vulcan`** `guards-refuse-package-swap` (`@venizia/vulcan`): the guards refuse `bun add`, `npm install`, `pnpm add`, `yarn add`, `link` and `patch` of it from anything but a registry version, a folder that is that package, or a registry or cache set on the install. What to do: add a registry version (`bun add @venizia/vulcan@^<version>`), or leave the change to the owner.
