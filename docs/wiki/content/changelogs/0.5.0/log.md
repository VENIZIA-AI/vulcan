This release makes the guards catch more of what an agent can do: more ways to write or delete a file they protect, more ways to launch a package, and the package managers' ways of swapping in another `@venizia/vulcan`. If your project sets `BUN_OPTIONS`, `NODE_OPTIONS` or `BUN_CONFIG_*` in `claude.settings.env`, move them to your shell.

## Breaking
- **The hooks drop the loader variables** `launch-file-and-loader-variables` (`@venizia/vulcan`): the hooks remove `BUN_OPTIONS`, `NODE_OPTIONS` and `BUN_CONFIG_*` from their environment, and `vulcan sync` refuses them in `claude.settings.env`. What to do: if you set one of them in `claude.settings.env`, move it to your shell; `vulcan sync` tells you which.
- **`.agents/vulcan.local.json` is gone: its keys live in `.agents/local/profile.json`** `local-json-folds-into-profile` (`@venizia/vulcan`): the agents you chose, your own `board.agents`, `board.serve.autoStart`, `local.tmp` and `events.dir` are now keys of the one per-person file, `.agents/local/profile.json`, next to your profile (`vulcan profile` keeps them when it saves your answers and `vulcan profile reset` removes only the answers). `vulcan sync` moves the keys of the old file into the profile (a key the profile already has keeps its value, and the note names it) and deletes the old file when git does not track it; if git tracks it, the keys are moved first and the note says to run `git rm --cached .agents/vulcan.local.json` and delete the file; a key the profile does not take (a typo) stays in the old file, which stays too, and the note names it. Until sync has run, the hooks and `sync` still read the old file. The profile file is protected from an agent's writes like the old one. An unknown key in the profile is now refused by `vulcan doctor` (the profile is strict). What to do: run `vulcan sync`; a script that reads or writes `.agents/vulcan.local.json` uses `.agents/local/profile.json`.
- **The default scratch folder is `.agents/tmp`** `tmp-default-agents-tmp` (`@venizia/vulcan`): scratch files, `TMPDIR` of the session, the board log and `vulcan clean` use `.agents/tmp` instead of `.agents/local/tmp`: a shorter path (a browser's socket path fits in more checkouts, so a project that set `local.tmp: 'tmp'` only for that can drop it), outside `.agents/local/`. `vulcan sync` makes the folder and adds `/.agents/tmp/` to a committed `.gitignore`; `local.tmp` still replaces it. An old `.agents/local/tmp` is left alone, and `vulcan clean` lists and removes its old items like the new folder's. Rule V-B-08 names the new folder. What to do: run `vulcan sync`; a script, Makefile, workflow or doc that names `.agents/local/tmp` names `.agents/tmp`; remove the old folder when it is empty (`vulcan clean --tmp --yes` takes what is stale).
- **Claude Code's settings are never committed, and `bun install` writes them** `claude-settings-never-committed` (`@venizia/vulcan`): `.claude/settings.json` is written by `vulcan sync` in every clone, so `sync` adds `/.claude/settings.json` to a committed `.gitignore` that does not already ignore `.claude/`, and `vulcan doctor` warns when git tracks it (run `git rm --cached .claude/settings.json`). `vulcan init --preset` writes a `prepare` script into the root `package.json` so `bun install` runs `vulcan sync --quiet` (guarded: it does nothing when vulcan is not installed, notes a failing sync, exits 0 and reads no terminal); `vulcan init` in an existing directory leaves your `package.json` alone, and `vulcan doctor` notes a project with no such script and prints the line. `vulcan sync --quiet` prints only what changed. The first lines of the rules block in `AGENTS.md` now say: run `vulcan sync` (`bun install` runs it when the `package.json` has the `prepare` script) before you work; until then no guard is active. A machine with no stored choice of agents and no terminal takes `claude`; users of Codex, omp or pi run `vulcan sync --agents <list>` once. The script is POSIX `sh`: Windows is untested. What to do: `git rm --cached .claude/settings.json` if git tracks it, add the `prepare` script, and run `vulcan sync` in CI before any step that reads the manifest.
- **The manifest is split: the hooks' part is local, atlas's part is committed** `manifest-local-and-descriptor` (`@venizia/vulcan`, `@venizia/vulcan-atlas`): `vulcan sync` now writes `.agents/local/vulcan.manifest.json` (the whole manifest, gitignored, one per clone: the hooks, the board and `vulcan doctor` read it) and `.agents/atlas.manifest.json` (name, packages, layout, presets, knowledge, release, sources, atlas and the resolved theme: committed, generated). `.agents/vulcan.manifest.json` is no longer read by the hooks; `vulcan sync` keeps it as a data-only copy of the descriptor, committed, until the stable 0.5.0 release, because atlas of 0.5.0-6 and before reads a source's manifest only at that path and needs it to resolve the source's ref before it can pin a release tag (without it `vulcan migrate plan` and the `vulcan` source fail with `has no .agents/vulcan.manifest.json`). A newer atlas reads the descriptor first; the copy goes with the stable release. `vulcan doctor` names a missing or stale copy. A fresh clone, and a clone just upgraded, has no local manifest until `vulcan sync` runs: until then every ask is a deny and every write outside the project is refused (the same hold as an unreadable manifest), agent signatures in a commit message are refused, and the session digest says to run `vulcan sync`, a command that passes the guards. What to do: run `vulcan sync` and commit `.agents/atlas.manifest.json` and the copy `.agents/vulcan.manifest.json` (keep it tracked; its content is now the descriptor, not the old manifest), point your wiki config at the new file (a repository that copies the shared wiki theme takes the new `changelog-prereleases.ts` too), and run `vulcan sync` in CI before the tests and the gates.
- **The Claude Code launch file is gone** `claude-launch-file-dropped` (`@venizia/vulcan`): `vulcan sync` no longer writes `.agents/local/claude.launch.settings.json`, and the doctor note and the session-start launch warning that asked you to start Claude Code with it are removed; `sync` deletes a leftover the project's git does not track. The session start still sets `TMPDIR` for every command the agent runs, and now tells the agent to keep scratch there and not in the scratchpad Claude Code offers in /tmp, which `guard-outside` refuses. What to do: start Claude Code without `--settings .agents/local/claude.launch.settings.json`; to keep Claude Code's own temp files in the project, export `CLAUDE_CODE_TMPDIR` in your shell. `vulcan doctor` now warns about a browser socket that is too deep for every project, not only one that had the launch file.
- **The guards read more ways to write or delete a protected file** `guards-read-more-write-forms` (`@venizia/vulcan`): these are now protected like the project settings: a copy, a move, an install, a link or an extraction into the folder of a protected file; a pattern, `find -delete` or `git clean -x` that can reach one; an edit in place; and the files the agent integrations write for Codex, Antigravity, omp and pi (`.codex/hooks.json`, `.agents/hooks.json`, `.omp/hooks/pre/vulcan-guards.ts`, `.pi/extensions/vulcan-guards.ts`). `sed -i`, `perl -pi`, `truncate`, `tar`, `unzip` and `git init` outside the project now ask first, like any other write. What to do: if you extract an archive at the project root (`tar xf`, `unzip`) or clear `.agents/local/*`, use a subfolder instead (`tar xf a.tar -C dist`, `.agents/tmp/*`).
- **A package run through more launchers is refused like `bunx`** `guards-read-more-launchers` (`@venizia/vulcan`): the guards now refuse a package run through `taskset`, `flock`, `runuser`, `parallel`, `su -c`, `script -c` or `find -exec sh -c`, and also `bun create`, `npm init` with a package name, `npm create`, `pnpm create`, `yarn create` and `bun add -g`. `make runners-check` now finds the same forms in your docs or scripts, as it does for `bunx`: a `bun create`, an `npm init` with a package name, an `npm`, `pnpm` or `yarn` `create` and a `bun add -g`. What to do: add the package to the project's dependencies and run its bin from `node_modules/.bin`, or list it in `guard.runners.allow` (for a scaffolder such as `vite`, the name goes there).
- **A commit or a pull request needs a flow in a project that logs events** `flow-required-for-commit` (`@venizia/vulcan`): with `events.log` on and a `project.key` set, the git guard refuses `git commit`, `gh pr create` and `glab mr create` when no flow can be found, and prints the `vulcan event add --kind flow` command that makes one. A flow is found from the branch name, a `Flow: <id>` in the command, or the flow the session last opened. Projects with `events.log` off are not affected, and neither is a project with no `project.key` (it cannot make a flow, so it is not refused: set the key and run `vulcan sync` to turn the rule on). Make the flow first and name the branch with its id.
- **`digest.oftenDropped` adds to the shipped list instead of replacing it** `digest-add-replaces-often-dropped` (`@venizia/vulcan`): the ids a project lists are now added after the 11 ids VULCAN ships (`base/defaults.config.json`), as every array of the shipped layers is; a project that had put the ids in its own order loses that order, because the shipped ids come first. A project that listed fewer ids than the default used to drop the rest; to keep that, take the ids out with `remove: { 'digest.oftenDropped': [...] }`.
- **VULCAN ships a read-only allow list, and the venizia pack ships the stack's config** `config-defaults-from-base-and-pack` (`@venizia/vulcan`): every project now gets, in `.claude/settings.json` after `vulcan sync`, 42 allow lines for commands that only read (`ls`, `grep`, `jq`, `rg`, `git log`, `git diff`...) with 14 companion denies for flags that write a file or name a program (`date -s`, `rg --pre`, `git ... --output`, `git cat-file --filters`...). A shipped deny can refuse a command one of your own allow lines used to permit: take it out with `remove: { 'claude.settings.permissions.deny': [...] }`. A project with `packs: ['venizia']` also gets the presets `ignis` and `ardor`, the atlas sources `ignis`, `ardor` and `vulcan`, and five allow lines for `bun run typecheck|test|lint`, `bun test` and `bun check`. A standing `**/Dockerfile*` acknowledgement for container paths comes with the base. This loosens the permissions of every project on upgrade: run `vulcan config --effective` to see the result, `vulcan config --diff` to see which lines you wrote that are now repeated, and take out what you do not want with `remove`.
- **The venizia pack refuses writes outside the project and agent signatures by default** `pack-guard-and-commit-defaults` (`@venizia/vulcan`): a project with `packs: ['venizia']` now gets `guard.outside: 'deny'` and `commit.message.agent.signature: 'deny'` without writing them. A project that wants the earlier behaviour writes `guard: { outside: 'ask' }` and `commit: { message: { agent: { signature: 'allow' } } }`; a project that already wrote the same values can delete them (`vulcan config --diff` lists them, and `vulcan doctor` notes how many repeat the defaults). `vulcan doctor` also warns about a `remove` entry that matches nothing. What to do: run `vulcan sync` and commit what git tracks that it changed, `.agents/atlas.manifest.json` and, where the project commits it, `.claude/settings.json` (with the signature denied, sync blanks the attribution Claude Code adds to a commit and a pull request); every clone runs `vulcan sync` once to install the commit-msg hook. Plan mode of Claude Code still writes its plan file under `~/.claude/plans` or `$CLAUDE_CONFIG_DIR/plans`: those folders are allowed as tool-owned paths.

- **Const classes lose `SCHEME_SET` and share a base, `ConstClass`** `const-classes-extend-const-class` (`@venizia/vulcan-atlas`, `@venizia/vulcan-okf`): the classes of the two packages that listed their values in a `SCHEME_SET` set (atlas: `Corpora`, `AtlasCommands`, `SkillSources`, `PackageKinds`, `LibraryKinds`, `AppSides`, `SourcePins`, `LogLevels`; okf: `ConceptStatuses`, `IssueSeverities`, `ReservedFiles`) now extend `ConstClass`. `X.SCHEME_SET` is gone; `X.values()` returns the values as a list and `X.isValid(value)` checks one and narrows its type. What to do: replace `X.SCHEME_SET.has(v)` with `X.isValid(v)` and `[...X.SCHEME_SET]` or a loop over it with `X.values()`.
- **`vulcan visualize` pages are simpler, and the spec changes with them** `visualize-pages-simplified` (`@venizia/vulcan`): a page is one light column with a head, a contents line, your actions, the decisions, the steps and the background, in that order, and it has no dark top slab, no dark footer and no kicker labels. A decision is a question that ends with `?`, two or three options with exactly one recommended, and a reason (`question`, `options`, `why`, `detail`); a step name is at most 40 characters and its note 80; a title is at most 60; a written section takes typed blocks (`sections`). A spec is now refused if it has `titleMuted`, `tiles`, `caption` or `language`, a title over 60 characters, a decision with `recommended` and `changes`, or a code-like question or option label. The page language is the owner profile's language, else English. A page for the owner (steps, actions or decisions) has no Present button.

## Added
- **Atlas finds an export by what you need: the `intent` tool** `atlas-intent-tool` (`@venizia/vulcan-atlas`, `@venizia/vulcan`): say the need in plain words ("wait 500 ms") and `intent` names the export that already does it, with its import line, signature, what it replaces and an example, read from the `@useWhen`, `@insteadOf` and `@example` tags of the package's TSDoc, on an export, on an `export * as X from` statement, or on a public static class member (found as `Class.member`, such as `PromiseUtility.sleep`); an export reached through several entry points is one hit, imported from the package that declares it; a miss says so and lists the closest names. The `build-a-feature` skill asks it before a helper is written by hand. What to do: nothing; a package without the tags is still found by its name and prose.
- **The `venizia` rule pack names a class by what it is** `rule-v-c-21` (`@venizia/vulcan`): the new rule `V-C-21` gives every class a name that tells you what it is. An object you create or bind that holds state is a `XxxHelper`, in `helpers/`, extending `BaseHelper`. Every other class is static: an access point to one thing is named after it with no suffix (`RuntimeConfig`, `AppEnv`), a bag of pure functions is a `XxxUtility` in `utilities/`, a class with a clear role is named for it (`Reader`, `Builder`, `Encoder`, `Factory`, `Registry`, `Store`, `Guard`), and a class of constants is named for its group (`HTTP`, `RequestTypes`). One protocol keeps one constants namespace and one class prefix. What to do: nothing, unless your project lists `packs: ['venizia']`; then run `vulcan sync` to receive the rule.
- **Atlas answers from the last good index at once, and says how far a source has got** `atlas-serves-last-good-index` (`@venizia/vulcan-atlas`, `@venizia/vulcan`): the server records each source it built in `.agents/local/cache/atlas/status.json` and, on the next start, serves it from that index immediately while a child checks the remote; the fresh index replaces it in place, and a remote that is down no longer takes a source away. An older index is served only while it is still what a fresh start would serve: the same source, a complete set of this atlas's index format, and, for docs pinned to the installed version, the same tag the installed packages decide now; after `bun update` or an atlas upgrade the source is built from nothing. `vulcan migrate` and `vulcan x atlas tools` always wait for the fresh build. The `notServed` notice changed shape and wording: its `message` now opens with `N of M sources are ready` (the project counted on both sides) and names each source that is building (seconds so far, the usual time, when to ask again), served from an older commit or tag while it refreshes, or not refreshable; new fields `ready`, `building`, `stale` and `retryInSeconds` carry the same, so the warning `vulcan migrate` prints for an unserved source reads differently. `vulcan x atlas status` prints the record (exit 1 on a source never served or a build hung in a live server) and `vulcan doctor` warns about the same and about a failed refresh. What to do: nothing. The first start of a source with nothing recorded builds as before (and so does the first start after this release); later starts answer at once.
- **`vulcan visualize` draws more kinds of chart and chooses the form from the data** `visualize-charts-chosen-from-data` (`@venizia/vulcan`): findings take `stack` (parts across groups), `meter` (value against a limit), `table` (exact values) and a `trend` line on a number. A `bar` of three values or fewer is a stat line, one over dates is a line, names are ranked bars and a negative value draws bars around zero; a `donut` is one segmented bar up to five parts and ranked bars beyond, and is never a ring; a `line` can mark one series with `emphasis`; a list of more than eight short items takes two columns. The label under a number tile is now sentence case at 13 px, not small capitals. Charts may now have up to 5 series, 12 parts and 6 charts per page. Specs that worked keep working.
- **You can set `board.agents` and `local.tmp` for your own checkout** `local-board-agents-and-tmp` (`@venizia/vulcan`): a team project no longer has to commit a personal board roster or a short temporary folder. Add `board.agents` and `local.tmp` to your gitignored `.agents/local/profile.json`, in the same shape as in the config, and they replace the committed value of the same key on your machine: the board page, the guards and `vulcan clean` use them, while `AGENTS.md` and the manifest still hold the team's values only. `vulcan sync` keeps these keys when it writes your agents and lists a local `tmp` folder in `.git/info/exclude`, `vulcan doctor` names the file and key of a value it cannot use, and the file is now protected from an agent's writes.
- **You can set `events.dir` for your own checkout** `local-events-dir` (`@venizia/vulcan`): a shared event folder for a coordinator (a hub session above several repositories) is a path of one machine, which no longer has to be committed. Put `"events": { "dir": "/absolute/path" }` in your gitignored `.agents/local/profile.json`: it replaces `events.dir` of the config on your machine, for the hooks, `vulcan event`, `vulcan board`, `vulcan clean --events`, the token meter and the guards, while the manifest and every committed file stay as they are. A value that is not an absolute path is not used by the hooks and the other readers (the committed folder applies), `vulcan sync` refuses until it is fixed, and `vulcan sync` and `vulcan doctor` name the file and the key. A linked worktree or a clone has its own file. `events.log` stays in the committed config.
- **`vulcan event step` changes one step of a flow, and a Claude Code task list fills the steps** `event-step-and-todo-mirror` (`@venizia/vulcan`): `vulcan event step --flow <id> --done "<step>"` (or `--todo`, `--next`, `--context`) updates a flow without restating its lists; it copies the flow's last line whole and writes it again with the change. In a project with `events.log` on, the `TodoWrite` list of a Claude Code session is merged into the steps of the flow the branch or the session last opened and that is not over: new tasks are added, completed ones are marked done, and nothing is removed or reopened, so an agent that keeps a task list needs no second step to keep the board true. A subagent's list is ignored. The hook reads only the text and the state of each task, cleaned and redacted.
- **The board shows a session with a running subagent as working** `subagent-start-signal` (`@venizia/vulcan`): with `events.log` on, `vulcan sync` adds a `SubagentStart` hook that writes a `subagent-start` line (the agent type and id, nothing else), so a long subagent no longer leaves its session looking idle. `vulcan event add --kind` accepts `subagent-start`. What to do: run `vulcan sync` and commit `.claude/settings.json`.
- **A turn that a user prompt starts begins with the flow and its open steps** `prompt-context-hook` (`@venizia/vulcan`): with `events.log` on, `vulcan sync` adds a `UserPromptSubmit` hook that tells the agent the flow it works on, up to five open steps and the exact `vulcan event step` command. It reaches only turns that a user prompt starts; a turn a peer message starts is still covered by the Stop hold. What to do: run `vulcan sync` and commit `.claude/settings.json`.
- **The board can start with the session, on your machine** `board-serve-autostart` (`@venizia/vulcan`): `board.serve.autoStart: true` in your own `.agents/local/profile.json` makes the `SessionStart` hook start `vulcan board serve --port 4317` when the event log is on and no VULCAN board answers there; another program on the port is left alone. An explicit `--port` of `vulcan board serve` is now strict: a busy port is an error (`board: cannot serve`) and no longer a fallback to another port. The output, with the address and its token, goes to `.agents/tmp/board-serve.log`. What to do: nothing, unless you want it; a script that relied on the fallback with `--port` drops the flag.
- **A flow left with open steps for two hours is raised once** `stale-flow-reminder` (`@venizia/vulcan`): the Stop hook of a project with `events.log` on holds a turn once when the session's flow has open steps and no line of work for two hours, with the exact `vulcan event step` commands, and then leaves the session alone for two hours. What to do: nothing; tick what is done, or say what comes next.
- **A Claude Code turn cannot end with the board out of step** `board-stop-hook` (`@venizia/vulcan`): in a project with `events.log` on, `vulcan sync` installs a `Stop` hook. When the session committed, opened a pull request, edited tracked files (when it already has a line in the flow) or merged a pull request of the flow and the flow has no newer line, it holds the end of the turn once and prints the exact `vulcan event step` command to run, with the open steps ready to tick. To know a commit or a pull request happened, the event hook now also runs after `Bash` calls and writes a `commit` or `pr` line with a fixed label; the command itself is never stored. Run `vulcan sync` to install it. Codex, Antigravity, omp and pi have no such hook and keep the V-P-13 rule.
- **The board shows the tokens a flow used** `board-token-usage` (`@venizia/vulcan`): in a project with `events.log` on, the `Stop` and `SubagentStop` hooks of Claude Code write `usage` lines: the input, output, cache read and cache write tokens of a session and of its subagents, with the model and the agent, on the flow they worked on (or on none). `vulcan board` adds them up per flow and shows a row for each agent and model. It counts tokens only; there is no price or cost anywhere. A session whose transcript is over 128 MB when the hook first sees it counts only what comes after. Codex, Antigravity, omp and pi are not covered.
- **The board shows the work items as cards, compact lines or a table, and marks stale work** `board-views-and-stale` (`@venizia/vulcan`): the **Work items** pane has a switch for three views. **Cards** is the view you had. **Compact** is one line per item: the code, the title, the stage, the steps done and the time of the last update; the `c` key switches between compact and cards. **Table** has the columns code, title, stage, state, holder, steps, PR and CI, tokens, due day and last update; it starts with the items that need you, then the latest update, and a click on a column heading sorts by it, up, then down, then back to that order. Filters for the agent, the repository and the state, and a **Stale** switch, narrow every view the same way. An item is **stale** when it is Running or Blocked, has a step still open and has had no line for two hours; a line that ticks a step counts. Your view and the table's sort are kept in the browser, like your language and theme.
- **The config can come from shipped defaults, and `vulcan config` shows it** `config-layers` (`@venizia/vulcan`): the config the commands read is now the shipped defaults (`base/defaults.config.json`), then the config of each rule pack in `packs` (`base/packs/<name>.config.json`), then your file, merged as data: objects by key, arrays add, scalars are overridden by the later layer. A new `remove` key in your file takes items out of an array a shipped layer added, such as `atlas.sources`. `vulcan config --effective` prints the merged config with the layer each value came from, and `--diff` lists the values your file repeats from a shipped layer. This release ships both files empty, so no project changes; the defaults that move in later are announced as they land.

## Changed
- **Rule `V-C-08` says a validated const class extends `ConstClass`** `rule-v-c-08-const-class` (`@venizia/vulcan`): the `venizia` pack no longer asks for a hand-written `SCHEME_SET` and `isValid`; a validated const class extends a base that gives `values()` and `isValid(value)`. In a project on IGNIS or ARDOR the base is `import { ConstClass } from '@venizia/ignis-helpers/common'`, not a copy. What to do: nothing, unless your project follows the pack and wants its classes to match.
- **`packages` is derived from the workspaces when the config does not write it** `packages-from-workspaces` (`@venizia/vulcan`): a project with workspaces no longer has to list each package by hand. Without a `packages` key, VULCAN reads the root `package.json` `workspaces` and each member's `package.json` and uses `{ dir, name, path }` for each, in the order of the paths; a list you write, even `[]`, stays exactly the list. `vulcan config --effective` shows the derived list, and `vulcan doctor` warns about a workspace member a written list does not name. A project with workspaces and no `packages` already failed `vulcan doctor`; now it passes when its members have names, and `vulcan sync` writes the derived packages into the manifest. What to do: if you tag releases per package, write `packages` with the dirs you want before the first release, because a derived `dir` follows the folder path (with the default `tagPattern`, `<dir>-v<version>`). In a git repository only members whose `package.json` is tracked are derived.
- **Supported runtime: Bun 1.4 or newer** `supported-bun-version` (`@venizia/vulcan`, `@venizia/vulcan-atlas`, `@venizia/vulcan-okf`): the packages now accept Bun 1.4 and newer (`engines.bun` is `>=1.4`). We recommend Bun 1.4.5, a security release with TLS, HTTP and DNS fixes, but you do not have to upgrade. If you contribute to VULCAN, you need Bun 1.4.4 or newer to run `bun check`.
- **`vulcan migrate plan` counts mentions, not breakages** `plan-counts-mentions` (`@venizia/vulcan-atlas`): the headline and the list under each step were worded as "found in your code", which read as "you are broken in this many places". The headline counts the steps with mentions, and each step lists the places that name a changed symbol; only some of those break. The wording is now "mentions in your code (places that name a changed symbol; check each)", and a step with none says "No mention found". The counting is unchanged. What to do: nothing; read each mention against the step.
- **`vulcan visualize` pages put the answer first and read quieter** `visualize-pages-quieter` (`@venizia/vulcan`): your actions sit under the contents line with no heading of their own, and the ask line is not drawn when there are actions. A decision is a flat block with a hairline above it and ruled option rows. The capital labels of the lifecycle, the before and after list and the decision record are gone (a lifecycle state keeps its kind as a tooltip), the decision record uses plain headings, and its option cards and the comparison cards are bordered, not filled; the recommended one has an accent border. ## Fixed
- **`vulcan event add --kind flow` with no `--flow` always makes a new flow** `flow-add-always-new` (`@venizia/vulcan`): on a branch that named an open flow it silently rewrote that flow's title, reason and steps. A flow line with no `--flow` is now a new flow whatever the branch; to change a flow give `--flow <id>` or use `vulcan event step`. The branch id still places the other lines of a flow. What to do: to update a flow, pass `--flow <id>` (or use `vulcan event step`); a flow line written with no `--flow` on a flow's branch now shows on the board as a second flow, where it used to rewrite the first.
- **`vulcan runners check` gives the answer CI gives** `runners-check-ignores-guard-variables` (`@venizia/vulcan`): the command now reads the project's `guard.runners.allow` and ignores what `VULCAN_GUARD_ASKS` and `VULCAN_GUARD_OUTSIDE` hold, so your local result matches CI.
- **`vulcan migrate apply` keeps the text of a step its codemod ran** `apply-keeps-step-text-after-codemod` (`@venizia/vulcan-atlas`): `apply` treated a step as done when its codemod exited `0` and printed only its `Data:` note, which hid the instructions of a codemod that lists places or rewrites some and leaves the rest. The step's text is now printed under "After the codemod, check each place it listed", with its `Data:` line. What to do: nothing; read each listed place against the step.
- **`vulcan migrate plan` reads the steps of a newer line for a pinned source** `plan-reads-folders-of-pinned-source` (`@venizia/vulcan-atlas`): a source pinned to the release of the package you have installed kept the newer releases in its table, but read the version folders from the older tag, so a plan to a newer line (`0.5.0`) found no step and printed `0 structured steps` with nothing to say why. The plan now reads the folders from the source's ref, and when the folders it read hold none for the line of the newer end of the plan (for a downgrade, the installed one), it says so and points at the source's `ref` setting and `vulcan x atlas pull`. What to do: nothing; rerun the plan.
- **`vulcan migrate apply` runs a second codemod over what the first wrote** `apply-stages-between-codemods` (`@venizia/vulcan-atlas`): `apply` ran each codemod as `. --write` in turn, and a codemod that refuses files with unsaved changes (the `devz` of `@venizia/dev-configs`) refused what the one before it had just written, so a plan with two codemods, such as the one from 0.4.8 to 0.5.0, failed at the second. After each codemod that ran, `apply` now stages what it wrote (`git add -A`) and leaves the result staged: review it with `git diff --staged`; the steps that stay manual come after it. The app must still be clean at the start (nothing unstaged, staged or untracked), as before; a forced run over a tree with changes of its own stages nothing. What to do: nothing; rerun `apply`.

## Security
- **The guards refuse a package manager's way of swapping in another `@venizia/vulcan`** `guards-refuse-package-swap` (`@venizia/vulcan`): the guards refuse `bun add`, `npm install`, `pnpm add`, `yarn add`, `link` and `patch` of it from anything but a registry version, a folder that is that package, or a registry or cache set on the install. What to do: add a registry version (`bun add @venizia/vulcan@^<version>`), or leave the change to the owner.
