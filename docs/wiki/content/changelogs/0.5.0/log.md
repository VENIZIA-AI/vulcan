This release makes the guards catch more of what an agent can do: more ways to write or delete a file they protect, more ways to launch a package, and the package managers' ways of swapping in another `@venizia/vulcan`. If your project sets `BUN_OPTIONS`, `NODE_OPTIONS` or `BUN_CONFIG_*` in `claude.settings.env`, move them to your shell.

## Breaking
- **The launch file is protected and the hooks drop the loader variables** `launch-file-and-loader-variables` (`@venizia/vulcan`): the launch file `.agents/local/claude.launch.settings.json` is now protected like the project settings, so an agent cannot write it. The hooks remove `BUN_OPTIONS`, `NODE_OPTIONS` and `BUN_CONFIG_*` from their environment, and `vulcan sync` refuses them in `claude.settings.env`. What to do: if you set one of them in `claude.settings.env`, move it to your shell; `vulcan sync` tells you which.
- **The guards read more ways to write or delete a protected file** `guards-read-more-write-forms` (`@venizia/vulcan`): these are now protected like the project settings: a copy, a move, an install, a link or an extraction into the folder of a protected file; a pattern, `find -delete` or `git clean -x` that can reach one; an edit in place; and the files the agent integrations write for Codex, Antigravity, omp and pi (`.codex/hooks.json`, `.agents/hooks.json`, `.omp/hooks/pre/vulcan-guards.ts`, `.pi/extensions/vulcan-guards.ts`). `sed -i`, `perl -pi`, `truncate`, `tar`, `unzip` and `git init` outside the project now ask first, like any other write. What to do: if you extract an archive at the project root (`tar xf`, `unzip`) or clear `.agents/local/*`, use a subfolder instead (`tar xf a.tar -C dist`, `.agents/local/tmp/*`).
- **A package run through more launchers is refused like `bunx`** `guards-read-more-launchers` (`@venizia/vulcan`): the guards now refuse a package run through `taskset`, `flock`, `runuser`, `parallel`, `su -c`, `script -c` or `find -exec sh -c`, and also `bun create`, `npm init` with a package name, `npm create`, `pnpm create`, `yarn create` and `bun add -g`. `make runners-check` now finds the same forms in your docs or scripts, as it does for `bunx`: a `bun create`, an `npm init` with a package name, an `npm`, `pnpm` or `yarn` `create` and a `bun add -g`. What to do: add the package to the project's dependencies and run its bin from `node_modules/.bin`, or list it in `guard.runners.allow` (for a scaffolder such as `vite`, the name goes there).
- **A commit or a pull request needs a flow in a project that logs events** `flow-required-for-commit` (`@venizia/vulcan`): with `events.log` on, the git guard refuses `git commit`, `gh pr create` and `glab mr create` when no flow can be found, and prints the `vulcan event add --kind flow` command that makes one. A flow is found from the branch name, a `Flow: <id>` in the command, or the flow the session last opened. Projects with `events.log` off are not affected. Make the flow first and name the branch with its id.

- **Const classes lose `SCHEME_SET` and share a base, `ConstClass`** `const-classes-extend-const-class` (`@venizia/vulcan-atlas`, `@venizia/vulcan-okf`): the classes of the two packages that listed their values in a `SCHEME_SET` set (atlas: `Corpora`, `AtlasCommands`, `SkillSources`, `PackageKinds`, `LibraryKinds`, `AppSides`, `SourcePins`, `LogLevels`; okf: `ConceptStatuses`, `IssueSeverities`, `ReservedFiles`) now extend `ConstClass`. `X.SCHEME_SET` is gone; `X.values()` returns the values as a list and `X.isValid(value)` checks one and narrows its type. What to do: replace `X.SCHEME_SET.has(v)` with `X.isValid(v)` and `[...X.SCHEME_SET]` or a loop over it with `X.values()`.
- **`vulcan visualize` pages are simpler, and the spec changes with them** `visualize-pages-simplified` (`@venizia/vulcan`): a page is one light column with a head, a contents line, your actions, the decisions, the steps and the background, in that order, and it has no dark top slab, no dark footer and no kicker labels. A decision is a question that ends with `?`, two or three options with exactly one recommended, and a reason (`question`, `options`, `why`, `detail`); a step name is at most 40 characters and its note 80; a title is at most 60; a written section takes typed blocks (`sections`). A spec is now refused if it has `titleMuted`, `tiles`, `caption` or `language`, a title over 60 characters, a decision with `recommended` and `changes`, or a code-like question or option label. The page language is the owner profile's language, else English. A page for the owner (steps, actions or decisions) has no Present button.

## Added
- **The `venizia` rule pack names a class by what it is** `rule-v-c-21` (`@venizia/vulcan`): the new rule `V-C-21` gives every class a name that tells you what it is. An object you create or bind that holds state is a `XxxHelper`, in `helpers/`, extending `BaseHelper`. Every other class is static: an access point to one thing is named after it with no suffix (`RuntimeConfig`, `AppEnv`), a bag of pure functions is a `XxxUtility` in `utilities/`, a class with a clear role is named for it (`Reader`, `Builder`, `Encoder`, `Factory`, `Registry`, `Store`, `Guard`), and a class of constants is named for its group (`HTTP`, `RequestTypes`). One protocol keeps one constants namespace and one class prefix. What to do: nothing, unless your project lists `packs: ['venizia']`; then run `vulcan sync` to receive the rule.
- **`vulcan visualize` draws more kinds of chart and chooses the form from the data** `visualize-charts-chosen-from-data` (`@venizia/vulcan`): findings take `stack` (parts across groups), `meter` (value against a limit), `table` (exact values) and a `trend` line on a number. A `bar` of three values or fewer is a stat line, one over dates is a line, names are ranked bars and a negative value draws bars around zero; a `donut` is one segmented bar up to five parts and ranked bars beyond, and is never a ring; a `line` can mark one series with `emphasis`; a list of more than eight short items takes two columns. The label under a number tile is now sentence case at 13 px, not small capitals. Charts may now have up to 5 series, 12 parts and 6 charts per page. Specs that worked keep working.
- **You can set `board.agents` and `local.tmp` for your own checkout** `local-board-agents-and-tmp` (`@venizia/vulcan`): a team project no longer has to commit a personal board roster or a short temporary folder. Add `board.agents` and `local.tmp` to your gitignored `.agents/vulcan.local.json`, in the same shape as in the config, and they replace the committed value of the same key on your machine: the board page, the guards, `vulcan clean` and the launch file use them, while `AGENTS.md` and the manifest still hold the team's values only. `vulcan sync` keeps these keys when it writes your agents and lists a local `tmp` folder in `.git/info/exclude`, `vulcan doctor` names the file and key of a value it cannot use, and the file is now protected from an agent's writes.
- **You can set `events.dir` for your own checkout** `local-events-dir` (`@venizia/vulcan`): a shared event folder for a coordinator (a hub session above several repositories) is a path of one machine, which no longer has to be committed. Put `"events": { "dir": "/absolute/path" }` in your gitignored `.agents/vulcan.local.json`: it replaces `events.dir` of the config on your machine, for the hooks, `vulcan event`, `vulcan board`, `vulcan clean --events`, the token meter and the guards, while the manifest and every committed file stay as they are. A value that is not an absolute path is not used by the hooks and the other readers (the committed folder applies), `vulcan sync` refuses until it is fixed, and `vulcan sync` and `vulcan doctor` name the file and the key. A linked worktree or a clone has its own file. `events.log` stays in the committed config.
- **`vulcan event step` changes one step of a flow, and a Claude Code task list fills the steps** `event-step-and-todo-mirror` (`@venizia/vulcan`): `vulcan event step --flow <id> --done "<step>"` (or `--todo`, `--next`, `--context`) updates a flow without restating its lists; it copies the flow's last line whole and writes it again with the change. In a project with `events.log` on, the `TodoWrite` list of a Claude Code session is merged into the steps of the flow the branch or the session last opened and that is not over: new tasks are added, completed ones are marked done, and nothing is removed or reopened, so an agent that keeps a task list needs no second step to keep the board true. A subagent's list is ignored. The hook reads only the text and the state of each task, cleaned and redacted.
- **A Claude Code turn cannot end with the board out of step** `board-stop-hook` (`@venizia/vulcan`): in a project with `events.log` on, `vulcan sync` installs a `Stop` hook. When the session committed, opened a pull request, edited tracked files (when it already has a line in the flow) or merged a pull request of the flow and the flow has no newer line, it holds the end of the turn once and prints the exact `vulcan event step` command to run, with the open steps ready to tick. To know a commit or a pull request happened, the event hook now also runs after `Bash` calls and writes a `commit` or `pr` line with a fixed label; the command itself is never stored. Run `vulcan sync` to install it. Codex, Antigravity, omp and pi have no such hook and keep the V-P-13 rule.
- **The board shows the tokens a flow used** `board-token-usage` (`@venizia/vulcan`): in a project with `events.log` on, the `Stop` and `SubagentStop` hooks of Claude Code write `usage` lines: the input, output, cache read and cache write tokens of a session and of its subagents, with the model and the agent, on the flow they worked on (or on none). `vulcan board` adds them up per flow and shows a row for each agent and model. It counts tokens only; there is no price or cost anywhere. A session whose transcript is over 128 MB when the hook first sees it counts only what comes after. Codex, Antigravity, omp and pi are not covered.
- **The config can come from shipped defaults, and `vulcan config` shows it** `config-layers` (`@venizia/vulcan`): the config the commands read is now the shipped defaults (`base/defaults.config.json`), then the config of each rule pack in `packs` (`base/packs/<name>.config.json`), then your file, merged as data: objects by key, arrays add, scalars are overridden by the later layer. A new `remove` key in your file takes items out of an array a shipped layer added, such as `atlas.sources`. `vulcan config --effective` prints the merged config with the layer each value came from, and `--diff` lists the values your file repeats from a shipped layer. This release ships both files empty, so no project changes; the defaults that move in later are announced as they land.

## Changed
- **Rule `V-C-08` says a validated const class extends `ConstClass`** `rule-v-c-08-const-class` (`@venizia/vulcan`): the `venizia` pack no longer asks for a hand-written `SCHEME_SET` and `isValid`; a validated const class extends a base that gives `values()` and `isValid(value)`. In a project on IGNIS or ARDOR the base is `import { ConstClass } from '@venizia/ignis-helpers/common'`, not a copy. What to do: nothing, unless your project follows the pack and wants its classes to match.
- **Supported runtime: Bun 1.4 or newer** `supported-bun-version` (`@venizia/vulcan`, `@venizia/vulcan-atlas`, `@venizia/vulcan-okf`): the packages now accept Bun 1.4 and newer (`engines.bun` is `>=1.4`). We recommend Bun 1.4.5, a security release with TLS, HTTP and DNS fixes, but you do not have to upgrade. If you contribute to VULCAN, you need Bun 1.4.4 or newer to run `bun check`.
- **`vulcan migrate plan` counts mentions, not breakages** `plan-counts-mentions` (`@venizia/vulcan-atlas`): the headline and the list under each step were worded as "found in your code", which read as "you are broken in this many places". The headline counts the steps with mentions, and each step lists the places that name a changed symbol; only some of those break. The wording is now "mentions in your code (places that name a changed symbol; check each)", and a step with none says "No mention found". The counting is unchanged. What to do: nothing; read each mention against the step.
- **`vulcan visualize` pages put the answer first and read quieter** `visualize-pages-quieter` (`@venizia/vulcan`): your actions sit under the contents line with no heading of their own, and the ask line is not drawn when there are actions. A decision is a flat block with a hairline above it and ruled option rows. A step not yet started shows its number; only done, in progress, waiting, blocked and dropped steps take an icon, and the key names only those. Sections are separated by a hairline and a smaller gap, and the theme switch sits at the right of the head instead of in a bar of its own.
- **`vulcan visualize` figures are light and wider, and the kinds drop their old labels** `visualize-figures-light` (`@venizia/vulcan`): a part with a figure (flow, architecture, compare, sequence, lifecycle, tree) is up to 1120 px wide while its heading and text stay on the 960 px edge, so a flow of four or more columns and a lifecycle of five states draw as figures at 1280 px instead of lists. Figure windows, the idea-map centre and the decision record's quote are light with a hairline, not dark slabs. The architecture figure orders the boxes of each layer to cross fewer lines. The tree sits on the text edge. The capital labels of the lifecycle, the before and after list and the decision record are gone (a lifecycle state keeps its kind as a tooltip), the decision record uses plain headings, and its option cards and the comparison cards are bordered, not filled; the recommended one has an accent border. A lifecycle of five states now takes two rows of three and two. The contents line no longer adds a second rule above the first section.

## Fixed
- **`vulcan runners check` gives the answer CI gives** `runners-check-ignores-guard-variables` (`@venizia/vulcan`): the command now reads the project's `guard.runners.allow` and ignores what `VULCAN_GUARD_ASKS` and `VULCAN_GUARD_OUTSIDE` hold, so your local result matches CI.
- **`vulcan migrate apply` keeps the text of a step its codemod ran** `apply-keeps-step-text-after-codemod` (`@venizia/vulcan-atlas`): `apply` treated a step as done when its codemod exited `0` and printed only its `Data:` note, which hid the instructions of a codemod that lists places or rewrites some and leaves the rest. The step's text is now printed under "After the codemod, check each place it listed", with its `Data:` line. What to do: nothing; read each listed place against the step.
- **`vulcan migrate plan` reads the steps of a newer line for a pinned source** `plan-reads-folders-of-pinned-source` (`@venizia/vulcan-atlas`): a source pinned to the release of the package you have installed kept the newer releases in its table, but read the version folders from the older tag, so a plan to a newer line (`0.5.0`) found no step and printed `0 structured steps` with nothing to say why. The plan now reads the folders from the source's ref, and when the folders it read hold none for the line of the newer end of the plan (for a downgrade, the installed one), it says so and points at the source's `ref` setting and `vulcan x atlas pull`. What to do: nothing; rerun the plan.
- **`vulcan migrate apply` runs a second codemod over what the first wrote** `apply-stages-between-codemods` (`@venizia/vulcan-atlas`): `apply` ran each codemod as `. --write` in turn, and a codemod that refuses files with unsaved changes (the `devz` of `@venizia/dev-configs`) refused what the one before it had just written, so a plan with two codemods, such as the one from 0.4.8 to 0.5.0, failed at the second. After each codemod that ran, `apply` now stages what it wrote (`git add -A`) and leaves the result staged: review it with `git diff --staged`; the steps that stay manual come after it. The app must still be clean at the start (nothing unstaged, staged or untracked), as before; a forced run over a tree with changes of its own stages nothing. What to do: nothing; rerun `apply`.

## Security
- **The guards refuse a package manager's way of swapping in another `@venizia/vulcan`** `guards-refuse-package-swap` (`@venizia/vulcan`): the guards refuse `bun add`, `npm install`, `pnpm add`, `yarn add`, `link` and `patch` of it from anything but a registry version, a folder that is that package, or a registry or cache set on the install. What to do: add a registry version (`bun add @venizia/vulcan@^<version>`), or leave the change to the owner.
